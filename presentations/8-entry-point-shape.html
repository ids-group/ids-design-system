Entry-point shape — four layouts, built

Deck 4 recommends option D with a per-component top layer, and the numbers behind it are settled. This is the sub-question that has to be answered before a line of it can be written, and it was not in the plan: what will the specifiers actually look like, and what does the library's folder layout have to become to get there.

The constraint that forces the question. An entry point's public specifier is the directory path relative to the package root, verbatim. There is no option to name an entry point — verified against all eight keys of the installed ng-package.schema.json, and confirmed by building a deliberately nested entry: a folder at deep/nested published as probelib/deep/nested with a FESM called probelib-deep-nested.mjs.

Our ng-package.json sits at the repo root and our sources live under src/lib/. So doing nothing about the layout gives specifiers like @ids-group-ltd/ids-design-system/src/lib/components/button.

Four layouts, each built for real

Prototypes at .claude/local/shape-probe/ — three libraries with the same content, plus a fourth shape built by post-processing the first one (a core plus two components), differing only in where the package root sits and how deep the component folders are. All of them built cleanly with ng-packagr; the maps below are copied from the exports field each build actually emitted.

Specifiers as clean as C, zero source moves, package root stays put, and the version trap never arises because there is no second package.json.

E was missing from the first version of this deck, and it is verified. A consumer app resolving the package from real node_modules — so the exports map is actually in play, which a tsconfig paths mapping would have bypassed — imported shapelib-a/button eagerly and shapelib-a/table from a lazy route:

  • resolved correctly under moduleResolution: bundler
  • placement correct — the lazy component appears 0 times in the initial bundle; 3 JS files, main plus one eager chunk plus one lazy chunk
  • one class identity — importing the same component through both the short alias and the long path emits same = At === At, the same minified binding on both sides, and the component definition selectors:[["s-button"]] appears exactly once

Its known wrinkle: ng-packagr identifies entry points by their real paths, so the library's own 307 cross-entry imports would be written with the long specifiers while consumers see the short ones. Two vocabularies — ugly inside, clean outside. Whether the internal ones can also be shortened is untested.

The 307 rewrites are the same number in every option, which is the thing that makes C cheaper than it first appears. An import that becomes a public specifier does not care how deep its file sits, so the 145 imports inside component folders that reach above components/ get rewritten once either way. C's genuinely extra work is 71 folder moves — mechanical git mv — plus finding a home for the 23 loose files that would otherwise collide at src/lib/, plus fixing depth on the intra-core relative imports that stay relative.

The version trap — it hits B and C, and E sidesteps it entirely

Today there is one package.json, at the repo root. It holds the version, npm version bumps it, and ng-packagr copies that number into the published package. One file, one source of truth.

Move the package root to src/lib/ and ng-packagr stops reading the root package.json — it reads src/lib/package.json instead. Two files now carry a version. infrastructure/scripts/cut-release.sh:75 still reads ./package.json, so a release would bump one file and publish the number from the other. Silently wrong version on npm.

Two ways out, and this only needs deciding if B or C wins — under E the question never arises:

  • Generate src/lib/package.json from the root one in a prebuild step. One source of truth stays where it is, npm version and cut-release.sh do not change at all. The repo already generates committed files this way (tokens.generated.ts, component-api.generated.ts).
  • Move the version's home to src/lib/package.json and point cut-release.sh and npm version at it. Conceptually cleaner, but it edits a release chain that took real work to get right.

Every option needs a generated typesVersions, or it breaks legacy consumers

This was carried on deck 4 and on this page as an untested caveat. It is now measured, with @arethetypeswrong/cli run against the packed artifact — the tarball a consumer actually downloads, not the source tree.

Package shapenode10 — rootnode10 — a subpath
today, single entry point🟢—
entry points, as planned🥴 internal resolution error💀 resolution failed
entry points + typesVersions🟢🟢

So the plan as written would have broken a consumer on legacy moduleResolution: "node" — and not only for deep specifiers: the root breaks too, because the facade's .d.ts re-exports from subpaths that node10 cannot resolve. One generated field fixes every row: 

"typesVersions": { "*": { "core": ["types/…-core.d.ts"], "components/button": ["…"] } }

It applies to B, C and E identically, it is written by the same build step that emits the entry points, and it is not optional. Worth adding attw --pack ./dist/ds to the release gate while we are here — today's package passes, so it starts green.

Recommendation

E. It gives C's specifiers for A's churn: no source moves, no second package.json, no version trap, and the release chain is untouched. The price is one post-build script and two vocabularies — long specifiers inside the library, short ones for consumers.

B is the fallback if the two vocabularies are unacceptable, and it costs moving one file plus solving the version trap. It was the recommendation before E was found.

C is the one to pick if you want the source tree to match the public API — it is what Angular Material and @angular/cdk publish, and it is the only option where the internal and external specifiers are the same string. The extra churn is 71 git mvs rather than a second wave of import rewrites, and what it costs is a flat src/lib/ holding roughly ninety entries plus a decision about where the 23 loose files go.

Answered since the first version of this deck: legacy moduleResolution: "node" does break on subpath entry points, and a generated typesVersions fixes it — see the section above. Still not verified: whether the library's own cross-entry imports can use the short specifiers under option E, or whether they must carry the long ones.
