MBP-133 — one entry point, and the four ways out

Status: deferred by decision (2026-08-21), deck for when it is picked up. Every number here is from docs/packaging-chunking-audit.md — measured, either in the consumer's build or in controlled esbuild 0.27.3 fixtures. Nothing on this page is an estimate.

The mechanism, in one paragraph

ng-package.json declares a single entryFile, so the package ships as one 1.25 MB FESM behind a single "." export. Tree-shaking works — unused components are dropped, verified twice. What cannot happen is chunk placement: esbuild splits by MODULE, and one FESM is one module, so it can never put two DS symbols in two different chunks. The moment an eager graph touches one symbol, the chunk carrying every DS symbol the app uses anywhere becomes a static import of main.

In mm-broker that one symbol is a service: provideCommon → NotificationService → ToastNotificationService → ToastService. Result: 632 kB of a 720 kB initial bundle — 88% — in an app where every feature route is lazy.

Two claims in the original filing are wrong, and the audit says so. It was never a tree-shaking failure (nobody upstream claimed it was), and "the consumer has no lever" is false — a dynamic import() in the eager root keeps main clean. It just costs tree-shaking, measured below. Also: this was never filed upstream as an ask; it is the consumer's own backlog item with a consumer-side fix available.

The fixtures, isolated

Identical payload each time: one tiny eagerly-needed export (toastService, 3 lines) and three heavy ones (400 lines each) — two used only by a lazy route, one used by nobody. Bars show what main pulls eagerly against what waits for the route.

A — today 40.1 kb eager
B — services entry 39.9 kb lazy
C — consumer import() 60.6 kb lazy

Bar width is the measured chunk size against the largest (60.6 kb), so B and A are the same SIZE and differ only in WHERE they land — which is the whole point. C defers everything too, and pays 50% more to do it.

The grep counts inside variant A's eager chunk are the proof, and they are what a summary would lose: 

toast-payload        3     ← eagerly needed, correct
table-payload      400     ← lazy-route-only, in the EAGER chunk
datePicker-payload 400     ← lazy-route-only, in the EAGER chunk
neverUsed-payload    0     ← tree-shaking works

Variant C is the consumer-side lever, and its cost is visible in the yellow: making the module a dynamic-import target turns it into an entry point, so unused exports can no longer be dropped. neverUsed-payload reappears at 400 hits and the chunk grows 40.1 → 60.6 kb, +50%. At library scale that is the difference between deferring the ~632 kB retained set and deferring the whole 1.25 MB FESM.

The four options

OptionWhat shipsPlacement fixedTree-shaking keptCost
A · do nothing Nothing. The consumer moves their provider or lives with it. no yes Defensible: their routes are all lazy anyway, so the chunk arrives with the first route. But every consumer rediscovers it, and the DS keeps a 1.25 MB single module.
B · one services entry point A second ng-package.json for ToastService, ModalService, BodyScrollLockService; root public-api.ts stays as a facade. yes yes Import paths change for anyone reaching those services directly — a major. No cross-entry deep-import refactor across the component folders, which is what makes it the cheap one.
C · leave it to consumers A documented recipe: await import('@ids-group-ltd/ids-design-system') in the eager root. yes no +50% on the deferred chunk, measured. And it has to be rediscovered by every consumer, which is what the last two audits were about.
D · per-component entry points One entry per component — the ideal end state. yes yes Forces every cross-entry deep import through a public entry: a large refactor across 85 component folders, and it moves every consumer's imports. Same major as B, far more work.

Recommendation when this is picked up: B, and only B.

  • It is the only option measured to fix placement without losing tree-shaking — C loses it, A fixes nothing.
  • The public API surface does not change: same symbols, same names, narrower specifiers. That keeps the migration to one find-and-replace per consumer.
  • It is a major either way, so it sequences with the other members of the breaking batch rather than shipping alone.
  • D is not wrong, it is just B plus a refactor nobody has asked for. If B turns out to be too coarse in practice, D is still available afterwards.

What would change the recommendation: a consumer whose eager root needs a COMPONENT rather than a service. B does nothing for that case, and it would be the argument for D.
