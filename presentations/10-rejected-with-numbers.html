Rejected, and the number that rejected it

Six ideas were investigated and not built. Each card carries what it would have bought, what it would have cost, and the condition under which it should be reopened — so a rejection can be argued with against a figure rather than against a summary.

One of the six has already been reversed by exactly that argument. A3-pre was declined at "40 import rewrites for 593 bytes". Challenged on the grounds that effort is not a reason, it was recomputed properly: the minimum cut is 14 rewrites, and the case for doing it was never the bytes. It is now on the build list. The rest of this page invites the same treatment.

REVERSED 2026-09-02 — now on the build list

De-cycle the core, so ds-card is not stuck in the bottom layer

Would buy
593 B gzip — and, the part that actually matters, it removes a layering inversion: ds-config.ts type-imports CardElevation and CardPadding from a component, so the config knows about something that depends on it.
Was priced at
40 import rewrites — wrong, and it was my figure. It assumed icons.data.ts (28 importers) had to move.
Actually costs
14 import rewrites: config/ds-config.ts → core (11) and components/card/card.types.ts → core (3). Found by searching every subset of candidate moves for the cheapest one that breaks the cycle. What remains is core ↔ icons, which costs nothing — icons has in-degree 38 and was always going to live in core.
Verdict
Do it, as the first commit of the entry-point work, so the layering fix is reviewable apart from the 307 mechanical rewrites.
REJECTED

basic + advanced as two npm packages

Would buy
18 KB gzip — the whole cost of the 52 components a prototype never touches. The entire library is 179 KB gzip; the entry cost is 5.6 KB.
Would cost
a second ds-table to keep in sync forever, a doubled release pipeline, and a template rewrite every time a prototype graduates to production.
Reopen if
a component ever needs an external runtime dependency — a charting renderer, for instance. That, not component count, is what justifies a separate package. ids-charts qualifies the day it needs one.
Corroboration (reported by the vendor, not measured here)
AG Grid 33 went the other way: 25 npm packages collapsed into 2, tree-shaking inside one package, grids reported up to 40% smaller. The biggest data-grid vendor moved away from package-per-feature. No source is cited for the 40% anywhere in this repo.
REJECTED

Semantic clustering of entry points, instead of one per component

Would buy
6 entry points instead of 77, and 53 fewer import rewrites (265 against 318) — 16.7%.
Would cost
almost all of the prize. Re-tested properly after a challenge: a cluster graph is made acyclic by merging its strongly-connected components, and data, fields, display and shell all merge into one.
What it becomes
3 clusters, one holding 60 of the 77 groups. That is the three-layer partition again, already measured as giving an eager-shell consumer roughly nothing. A lazy route using ds-table would drag 59 sibling groups.
Why it cannot be fixed
the cycle is made of real edges — pagination → select, autocomplete → tag, multi-select → badge, empty-state → loading-overlay. Components compose across semantic categories, so the categories do not match the dependency graph. A different set of categories would meet the same edges.
REJECTED

Split the icon map so unused icons drop

Would buy
≤ 2 522 B gzip — measured by cutting the map from 86 icons to 9 and rebuilding: ds-button went 62 733 → 60 211 B gzip. That is the whole icon set; SVG path strings compress to almost nothing.
Would cost
two public APIs. IconName = keyof typeof ICONS is derived from the map, and provideDsIcons merges into it — both break — plus every by-name icon reference needs a different mechanism.
Reopen if
the set grows to roughly 500 icons. At about 22 B gzip per icon that would be ~11 KB, which changes the answer. Also reopen if we ever ship illustrations rather than 24×24 paths.
NOT REJECTED — already used, just has no work left

A build-time define flag beyond dev warnings

It works
measured: a 500-line branch removed from a published FESM, 123 498 → 99 550 B raw. We already use it — the dev-warning fix is exactly this, and it shipped 1 590 B gzip.
Why not more
nothing is left for it. Its niche is code that must ship but can be branched away with no seam to hang it on. Of 144 boolean flags in the library, nearly all are instance state (disabled, loading, required); everything substantial is a feature, and features are better served by a directive — no build flag, no two bundles, no silent no-op. The last cross-cutting candidate, staticPreview, is one boolean and about eight early returns: tens of bytes.
What it costs if used anyway
two bundles from one source, so CI must build both; the public API does not change, so a consumer can bind a flag that silently does nothing; and define is a textual substitution, so a typo means "not set" with no error.
Reopen if
substantial cross-cutting code appears that cannot be a directive — heavy runtime assertions, an accessibility debug layer.
REJECTED

Ship the portaled CSS inside the code, the way AG Grid does

Would buy
1 055 B gzip arriving with the feature instead of needing a consumer-side opt-in import — no styles.scss change for anyone.
Would cost
a Content Security Policy bill on every consumer. Angular injects styles as runtime <style> tags; a strict CSP needed unsafe-inline before Angular 16 and nonces after, and under SSR the static build-time tags carry no nonce so a strict CSP blocks them. A consumer has no control over how a library handles its styling.
Reopen if
the portaled CSS grows well past 1.6 KB, or Angular gains a supported way for a library to register global styles that participates in the app's nonce.
