Opt-in seam — 31.5 KB, three choices, no blockers

Every number here is measured, and none of it waits on the entry-point decision — this is retention (what is in the bundle at all), not placement (which chunk it lands in). Three related choices, one pattern, and one already-banked win that proves the pattern works.

18.9 KB Table grid features → directives. Ablation-measured; the table's marginal cost falls 31.4 → 12.1 KB gzip.
11.0 KB Button's message row. 35% of what one <ds-button> costs, paid by everyone who renders one.
1.6 KB Portaled overlay CSS → opt-in import. Only pays a consumer with no pickers, toasts or modals.
1.6 KB Already banked — dev warnings, shipped in d8eb81c0. Same pattern, zero API change.

The seam costs a fixed 923 bytes, and that is the whole risk

The obvious objection to splitting a feature out of a component is that the machinery costs more than the feature. Measured on a purpose-built fixture — a component owning a derived value, a per-instance contribution registry, and one optional feature in three shapes:

Feature sizeDeleted outrightInline, input off (today)Behind a directive, not importedSeam overheadRecovered
1.6 KB gzip32 965 B34 592 B33 888 B923 B704 B
5.9 KB gzip32 965 B38 901 B33 888 B923 B5 013 B

The "not imported" column is byte-identical at both feature sizes. The overhead is fixed — the service, its providers entry, the composition point — while recovery scales 1:1 with the feature. So for the table's 18.9 KB against one registry, the seam keeps roughly 87–95% of the prize. The honest other side: a consumer who does use the feature pays about 1 KB more than today.

Two libraries solved this already, and both landed in the same place

Searched before designing, not after. The two most-used data grids both rebuilt their feature architecture in the last release cycle, and neither chose a second package.

AG Grid 33TanStack Table v9
What they did collapsed 25 npm packages into 2, features tree-shake from one bundled package features are opt-in and registered per table; core stays tiny
API ModuleRegistry.registerModules([…]) globally, or modules: […] per grid tableFeatures({ rowPaginationFeature, … }) passed to the table
Reported result grids up to 40% smaller; 43% off one application's bundle a small table starts around 5 kB; the library grew 14 → 25 kB but the average table shrank
Second motive "2 packages instead of 25 means better velocity" — maintenance, not size the registered set narrows the TypeScript surface: an omitted feature's API does not exist

AG Grid's move is independent confirmation of the basic/advanced verdict on deck 5. The biggest data-grid vendor went away from package-per-feature towards tree-shaking inside one package — which is exactly what the basic/advanced proposal wanted to reverse.

TanStack's type narrowing is the one thing we cannot copy. An Angular component's inputs are fixed on the class; there is no way to make resizableColumns conditionally absent based on what a consumer registered. So the footgun this deck flags — binding a feature you did not import and getting silence — stays under every shape below. Worth knowing before anyone plans around a benefit we cannot have.

Choice 1 — the table's grid features

ds-table today 31 428 B
grid features split out 12 125 B

Marginal cost beside a prototype kit that already uses the rest of the library. Measured by deleting the features on a probe branch: column resize, reorder + the visibility picker (and with it the @angular/cdk/drag-drop import), column filters, CSV export, layout persistence, and truncate + cell popover — 1 063 source lines across .ts, .html and .scss.

18.9 KB is a floor, not a ceiling. Row actions and inline cell editing are equally advanced and were left in; the hard ceiling is 31.0 KB, since everything else the table does — sorting, selection, pagination, loading, sticky header, cell rendering — has to stay.

Why it is a registry rather than a method move

The ablation kept colliding with shared helpers: clipWidth/fitsContent serve both truncate and resize; orderedColumns/visibleColumns are the computed chain the picker writes to; filteredData folds set filters into the substring search; statusMessage folds export state into the live region. All four are the same pattern: the table owns a derived value and an optional feature wants to contribute an input to it. So the seam is a contribution registry, provided per table instance: 

@Injectable() // providers: [DsTableLayout] on ds-table itself
export class DsTableLayout<T> {
  readonly columnTransforms = signal<readonly ColumnTransform<T>[]>([]); // order, visibility, width
  readonly rowFilters       = signal<readonly RowFilter<T>[]>([]);
  readonly statusParts      = signal<readonly Signal<string | null>[]>([]);
  readonly headerAdornments = signal<readonly HeaderAdornment[]>([]);
}

visibleColumns becomes columns() piped through columnTransforms() — an empty array is the identity, which is exactly the ablated behaviour that already compiles and measures at 12.1 KB. Width resolution moves into the seam as one resolvedWidth(col) the table always calls, so neither resize nor truncate owns it. The table never names a feature — no if (resizable) anywhere.

Three shapes for the opt-in, and the choice is ergonomics — not size

All three tree-shake identically: an unimported directive, an uncalled feature function and an unreferenced provider are all dead code. They differ in where the wiring lives and what scope it has.

1a — directives1b — features input1c — provider features
What a consumer writes <ds-table dsResizable dsExport> [features]="[withResize(), withExport()]" provideDsTable(withResize(), withExport())
Scope per table instance per table instance route or app — every table under it gets the same set
Prior art Angular's own directive idiom TanStack Table v9 Angular's provideRouter(withViewTransitions()); AG Grid's per-grid modules
Invalid combinations not detectable checkable at runtime the documented pattern gives each feature a kind so combinations can be validated
Cost per feature a selector and a host binding one factory function one factory function

1c is the most Angular-idiomatic and the only one that validates combinations — but EnvironmentProviders is deliberately cross-cast so it cannot be used in component scope, which makes it route-wide. That is usually fine for a data-grid route and it is simpler wiring, but it is a real semantic difference: two tables on one page could not differ.

1a keeps per-instance control and reads naturally in a template, which is what the seam below was designed for. 1b is the same control with one input instead of N attributes, and it is what TanStack chose — but without their type narrowing, its advantage over 1a is mostly tidiness.

What a consumer writes under 1a:

<!-- prototype: nothing imported, nothing shipped -->
<ds-table [columns]="cols" [data]="rows" />

<!-- production: the feature arrives with the directive -->
imports: [DsTable, DsTableResizable, DsTableExport]
<ds-table dsResizable dsExport [columns]="cols" [data]="rows" />

Two genuinely hard bits, both known before starting. (1) A directive cannot inject markup, and the filter button, the resize handle and the picker popover ARE markup — the table keeps tiny @if (headerAdornments().length) slots rendering an ng-template the directive supplies, and the residual slot cost has to be measured rather than assumed. (2) clipWidth/fitsContent are only untangled by moving width resolution into the seam first.

ButtonComponent extends DsMessageBase and imports FieldMessageComponent so a button can render a hint, warning or error line under itself. 11 295 B gzip, paid by every consumer that renders one button, whether or not they ever bind hint.

Entry points do not fix this one — even per-component entries keep button → field-message as a static edge, so the 11 KB arrives with any button. Two ways out: drop the feature from ds-button, or move it behind an opt-in directive (DsButtonMessage) — the same seam, one contribution kind.

Choice 3 — the portaled overlay stylesheets

styles/ds.scss compiles to 58 293 B minified / 10 282 B gzip. An earlier version of this analysis claimed ~1.8 KB of it could move into component SCSS; that was wrong and the correction matters here:

PartialgzipWhat it isCan it move?
link533 Bthe public .link helper classno — it is API
page-grid, layout-utils496 Bpublic layout classesno
scrollbar297 Bstyles html and ::-webkit-scrollbarimpossible
skeleton-shimmer207 Bone :root animation so every skeleton stays in lock-stepno, by design
surface-motion192 B@keyframes; emulated encapsulation renames themno
dropdown-overlay, overlay-motion, toast-overlay1 592 Bportaled panels, rendered outside the component's DOMopt-in only

So the only lever is making the portaled group an opt-in import (@use 'styles/dropdown-overlay') rather than part of styles/ds. It pays 1.6 KB gzip, and only a consumer with no pickers, toasts or modals — rare. It is the smallest of the three and the one most reasonably declined.

AG Grid solves this differently, and their way costs more than it saves here. They keep CSS in the code so it splits per module — the style would arrive with the feature and vanish without it, needing no opt-in import at all.

The bill is Content Security Policy. Angular injects styles as runtime <style> tags; a strict CSP needed unsafe-inline before Angular 16, and 16+ adds nonces — but under SSR the static build-time tags in index.html carry no nonce and a strict CSP blocks them. A consumer has no control over how a library handles its styling, so injecting global CSS from our own code pushes a CSP and SSR burden onto every one of them. For 1.6 KB, not worth it.

Why a build-time flag is not the tool for any of these

A define flag in the consumer's angular.json genuinely does strip code from a published FESM — measured, 123 498 → 99 550 B raw with the branch gone. But its scope after the dev-warning fix is close to empty, and it is worth saying why so the idea is not re-opened:

Kind of codeRight tool
a whole component the app never usesnothing — tree-shaking already drops it
a separable feature of a component the app does usean opt-in directive — this deck
a branch inside code that must ship, with no seamdefine — dev warnings, and they are done
behaviour, not bytesDS_CONFIG — one provider, all components

The remaining cross-cutting candidate was staticPreview, the showcase-only input. By inspection it is one boolean on a host directive plus about eight early returns in modal, popover and select — tens of bytes, not worth a flag. So define has no further work here, and DS_CONFIG.prototype: true is a behaviour question worth zero bytes, which is a separate and much smaller decision.
