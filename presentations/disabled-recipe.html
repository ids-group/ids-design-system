Disabled, across every variant and state

The real case, read out of the consumer today. projects/common/components/src/lib/list-search/list-search.component.html renders <ds-button variant="ghost" size="sm" icon="x" [disabled]="!canClear()">Clear</ds-button> — ghost, and no color, so it takes the default primary. That is the pairing with the smallest gap in the whole matrix below.

Their fix does nothing, and their own comment says why they wrote it. _ds-overrides.scss sets --opacity-muted: var(--opacity-text-disabled) on ds-button and ds-icon-button, explaining that "the DS dims a disabled control to --opacity-muted (0.6)". It does not: neither component reads that token anywhere. The disabled state is three oklch(from accent …) colours, so the override is inert — the button they were trying to fix is unchanged to this day.

How to read a row. The second column is the button ALIVE — rest, hover, active — so you can judge the disabled box against what it is supposed to differ from. Then one column per candidate. Every box is painted with background-image gradients and inline colours, so a force-dark browser cannot rewrite them. vs rest is the contrast between the disabled label and the enabled one: under 1.8:1 the state is a guess, which is exactly the complaint.

What each candidate is. A is today. B changes only the two variants that have no fill, replacing the accent-derived label with the neutral --text-disabled. C keeps the accent HUE and only lifts lightness/chroma — one number, every variant.

The dark theme — the check I had skipped

"State contrast parity": a disabled state has to be as legible in dark as in light, and every number above this point was measured on white only. On a dark ground the light theme flips: the enabled label is a LIGHT blue (hsl(229 90% 72%)), so a recipe that pins 58% lightness makes disabled DARKER than enabled instead of lighter — the same direction of change, but arrived at from the other side. Worth reading before choosing.

C versus D — the difference is one row.

Both use the same recipe, oklch(from accent 70% 0.035 h): hue from the accent, lightness pinned brighter. C applies it to all five variants. D applies it to all except solid, which keeps today's 58%. Solid is singled out because its label does not sit on the page — it sits on the button's own 92%-lightness disabled fill, so lifting the label to 70% brings the two together: legibility drops from 3.38:1 to 2.11:1. Every other row in C and D is identical, so only the solid row is worth comparing.

Where this landed, and the measurement beat the plan three times.
  1. The filed cause was wrong. Neither ds-button nor ds-icon-button reads --opacity-muted, so the consumer override retuning it is inert — the Clear button they were fixing is untouched to this day.
  2. Four of five variants fail, not one. Solid repaints 4.32:1 when disabled; tonal moves 1.09:1 and outline 1.07:1 — nothing. And the fill table shows raising it cannot help: a tonal rest fill is already a 94%-lightness tint and every neutral surface we own is near-white.
  3. The dark theme then killed the light-theme front-runner. On a dark ground the enabled label is a LIGHT blue and --text-disabled is a dim grey, so the neutral-label candidates collapse to 1.59:1 — worse than what they fix in light. The recipe candidates manage 1.45–1.86.

The recommendation is G, scoped the way D scopes C: everywhere except solid. color-mix(in srgb, var(--_button-label-color) 50%, var(--surface-default)) — the label walks half-way to whatever the theme's ground is. That is the one thing opacity got right, expressed as a colour instead of transparency: nothing goes translucent, nothing shows the page through it, and it needs no per-theme value because the surface token already differs per theme.

The solid row is why G needs D's scoping: there the enabled label is WHITE, and mixing white into a white surface changes nothing (1.00:1), while the label's legibility against its own pale fill falls to 1.27:1. Solid keeps today's recipe — it is the one variant whose box already carries the state.

  • It must REPLACE the resolvers, not stack with them. Stacking is the bug fixed elsewhere this week: a disabled row wearing --text-disabled AND 0.6 opacity measured 1.68:1, almost invisible. One mechanism per state.
  • The cost, stated plainly: the disabled label becomes fainter than today — 2.16–2.45:1 in light where A gives 4.3–5.2, and 1.75:1 for dark tonal. Disabled text is exempt from WCAG contrast, and "faint" is the message, but this is the trade being made.
  • Still colour-only for a sighted user. cursor: not-allowed and the disabled attribute cover the pointer and the screen reader. Worth deciding whether ghost and text also drop their underline, or gain a faint fill, so the state has a second channel.

Nothing here is implemented. The only disabled change shipped this week is the removal of the double dimming on select / date-picker / time-picker / menu-item / dropdown rows. Opacity as a mechanism (candidate F) was measured and then dropped at Stas's call.
