Форма раскладки — какие специферы увидит потребитель

Ключевой факт: ng-packagr называет entry point по пути папки, дословно. Опции переименовать нет — значит структура папок становится публичным API навсегда. Для варианта F (дека 4) этот вопрос не возникает: точка остаётся одна.

Что видит потребитель

A  import { ButtonComponent } from '@ids/ds/src/lib/components/button';   ← раскладка наружу
B  import { ButtonComponent } from '@ids/ds/components/button';
C  import { ButtonComponent } from '@ids/ds/button';                      ← форма Material
E  import { ButtonComponent } from '@ids/ds/button';                      ← то же, без переездов

Ловушка с версией — бьёт по B и C

Корень пакета уезжает в src/lib → ng-packagr перестаёт читать корневой package.json, а cut-release.sh:75 читает именно его. Релиз поднимет одно число, опубликует другое: молча неверная версия в npm. Лечится генерацией src/lib/package.json из корневого в prebuild — репозиторий уже так делает для tokens.generated.ts.

typesVersions — нужен только E

Проверено резолвером TypeScript 5.9.3 на реальных фикстурах, с падающим негативным контролем:

node10bundlernode16
вывод ng-packagr, без typesVersions✓✓✓
короткий алиас без папки на диске (E)✗✓✓

Причина на диске: ng-packagr сам эмитит node10-заглушку на каждую точку. node10 игнорирует exports, находит папку, читает typings. У алиасов E папки нет — отсюда и typesVersions. Это единственная цена E, и она одно генерируемое поле.

Рекомендация: E

Специферы как у Material, ноль переездов, корень пакета на месте, релизный конвейер не трогаем. Проверено на настоящем node_modules (не через paths, иначе карта exports не участвует): резолвится, размещение верное — ленивый компонент в стартовом бандле 0 раз, и одна идентичность класса через короткий и длинный путь.

Шероховатость E: внутри библиотеки специферы длинные, снаружи короткие — два словаря. C — если важнее, чтобы диск совпадал со специферами.
