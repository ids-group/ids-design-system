Токены кнопок: «как сейчас в button» vs «как в badge»

Вопрос: где живут значения публичных токенов --ds-button-*. Подход A (сейчас в button/icon-button) — компонент объявляет токены на самом элементе. Подход B (сейчас в badge/tag/toast/empty-state) — компонент токены читает через var(--ds-…, дефолт), а полутона hover/active по дефолту считаются от базового цвета. Публичные токены — одни и те же в обоих подходах, API не меняется. Разница только в поведении — она ниже, вживую.

Сценарий 0

Из коробки — ничего не переопределяли

A — объявление (как сейчас)
наведи — hover, зажми — pressed

✓ Работает.

B — чтение с fallback (как в badge)
наведи — hover, зажми — pressed

✓ Работает. Пиксель в пиксель как A: дефолтная деривация (88% / 76% чёрного) — та же рецептура, что у --primary-hover / --primary-pressed в теме.

Сценарий 1

Потребитель задаёт ОДИН токен

.toolbar ds-button { --ds-button-bg: #0d9488; }   /* и больше НИЧЕГО */
Цвет бренда: применяется к сценариям 1–3
A — объявление (как сейчас)

✗ Проигнорировано. Собственное объявление токена на элементе всегда сильнее значения, унаследованного снаружи. Не пробивается ничем: ни селектором, ни :root, ни inline-стилем. Это сегодняшний баг ds-button / ds-icon-button.

B — чтение с fallback (как в badge)

✓ Один токен — и bg, hover, pressed, halo пересчитались сами. Наведи и зажми: полутона уже от нового цвета.

Сценарий 2

…но если захочу — точечно перепишу и active

.toolbar ds-button {
  --ds-button-bg: #0d9488;
  --ds-button-bg-active: #4c1d95;   /* своё значение вместо деривации */
}
A — объявление (как сейчас)

✗ Всё ещё игнор.

B — чтение с fallback (как в badge)

✓ Hover по-прежнему деривируется от bg, а pressed — фиолетовый, заданный руками. Точечное значение всегда побеждает деривацию: var(--ds-button-bg-active, …дефолт) сначала смотрит на ваше.

Сценарий 3

То же самое для ds-icon-button (filled / selected)

A — объявление (как сейчас)

✗ Игнор.

B — чтение с fallback (как в badge)

✓ Один --ds-icon-button-bg — hover/pressed сами.

Код

Что меняется внутри компонента (вариант error)

A — сейчас: каждый полутон задаётся отдельно
&.error {
  --ds-button-bg:        var(--error);
  --ds-button-bg-hover:  var(--error-hover);
  --ds-button-bg-active: var(--error-pressed);
}
B — станет: один цвет, полутона сами
&.error {
  --_button-bg: var(--ds-button-bg, var(--error));
  /* hover / active / halo — деривация от bg */
}

Приватный --_button-bg — внутренняя деталь («разрешённое значение»), снаружи не виден и не является API. Где деривация не к месту (secondary / tertiary / outline — пастельные и прозрачные фоны, чёрная подмесь даёт грязный тон), дефолты остаются явными ramp-значениями — но и там потребительский токен теперь будет работать.

Вердикт

Рекомендация: подход B — «как в badge»

  • «Как везде» — на самом деле не везде. Объявляют токены только старшие компоненты (button, icon-button, sidenav-item). Новые — badge, tag, toast, empty-state — уже читают с fallback. Это и есть актуальная конвенция репо; кнопки до неё просто не доехали.
  • Подход A чинить нечем: пока компонент объявляет публичный токен на своём элементе, сценарии 1–3 не работают в принципе — это правило каскада CSS, а не вопрос специфичности.
  • B даёт ровно вашу концепцию: из коробки само → один токен тянет полутона → любой токен точечно переписывается.
  • Визуально ничего не ломается: для primary / error / filled / selected дефолтная деривация совпадает с текущими цветами один в один; у success / warning появится чуть более тёмный pressed (сейчас он равен hover).
