Токены кнопок: «как сейчас в button» vs «как в badge»

Вопрос: где живут значения публичных токенов --ds-button-*. Подход A (сейчас в button/icon-button) — компонент объявляет токены на самом элементе. Подход B (сейчас в badge/tag/toast/empty-state) — компонент токены читает через var(--ds-…, дефолт), а полутона hover/active по дефолту считаются от базового цвета. Публичные токены — одни и те же в обоих подходах, API не меняется. Разница только в поведении — она ниже, вживую.

Сценарий 0

Из коробки — ничего не переопределяли

A — объявление (как сейчас)
наведи — hover, зажми — pressed

✓ Работает.

B — чтение с fallback (как в badge)
наведи — hover, зажми — pressed

✓ Работает. Пиксель в пиксель как A: дефолтная деривация (88% / 76% чёрного) — та же рецептура, что у --primary-hover / --primary-pressed в теме.

Сценарий 1

Потребитель задаёт ОДИН токен

.toolbar ds-button { --ds-button-bg-color: #0d9488; }   /* и больше НИЧЕГО */
Цвет бренда: применяется к сценариям 1–3
A — объявление (как сейчас)

✗ Проигнорировано. Собственное объявление токена на элементе сильнее значения, унаследованного снаружи: не работает ни селектор по хосту (даже с !important), ни :root, ни inline-стиль. Единственная лазейка — селектор ВНУТРЬ приватной структуры с хаком специфичности, т.е. завязка на внутренние классы вместо публичного API — живой пример в сценарии 1b ниже. Проверено Playwright'ом на собранном ds-docs (2026-06-10).

B — чтение с fallback (как в badge)

✓ Один токен — и bg, hover, pressed, halo пересчитались сами. Наведи и зажми: полутона уже от нового цвета.

Сценарий 1b

Лазейка в подходе A — хак специфичности внутрь компонента

/* так сегодня выживает field (_ds-overrides.scss, кейсы ds-banner / ds-tabs):
   селектор лезет в ПРИВАТНЫЙ .button, а дубль класса перебивает
   специфичность encapsulation-атрибута: .button.button (0,2,1) > .button[_ngcontent] (0,2,0) */
.toolbar ds-button .button.button { --ds-button-bg-color: #0d9488; }
A — объявление + хак (наведи и зажми!)

✗ Пробились — но в покое кнопка тиловая, а hover и pressed ОСТАЛИСЬ СИНИМИ: деривации в подходе A нет, каждый полутон надо так же переписывать руками (-bg-hover, -bg-active, halo…). Плюс завязка на приватный класс .button и дубль ради специфичности — сломается при любом рефакторинге внутренностей. Хак статичный (#0d9488), пикер из сценария 1 на него не влияет.

B — чтение с fallback: хак не нужен

✓ Тот же перекрас — одним токеном на хосте, без залезания внутрь, и полутона подтянулись сами.

Сценарий 2

…но если захочу — точечно перепишу и active

.toolbar ds-button {
  --ds-button-bg-color: #0d9488;
  --ds-button-bg-color-active: #4c1d95;   /* своё значение вместо деривации */
}
A — объявление (как сейчас)

✗ Всё ещё игнор.

B — чтение с fallback (как в badge)

✓ Hover по-прежнему деривируется от bg, а pressed — фиолетовый, заданный руками. Точечное значение всегда побеждает деривацию: var(--ds-button-bg-color-active, …дефолт) сначала смотрит на ваше.

Сценарий 3

То же самое для ds-icon-button (filled / selected)

A — объявление (как сейчас)

✗ Игнор.

B — чтение с fallback (как в badge)

✓ Один --ds-icon-button-bg-color — hover/pressed сами.

Код

Что меняется внутри компонента (вариант error)

A — сейчас: каждый полутон задаётся отдельно
&.error {
  --ds-button-bg-color:        var(--error);
  --ds-button-bg-color-hover:  var(--error-hover);
  --ds-button-bg-color-active: var(--error-pressed);
}
B — станет: один цвет, полутона сами
&.error {
  --_button-bg-color: var(--ds-button-bg-color, var(--error));
  /* hover / active / halo — деривация от bg */
}

Приватный --_button-bg-color — внутренняя деталь («разрешённое значение»), снаружи не виден и не является API. Где деривация не к месту (secondary / tertiary / outline — пастельные и прозрачные фоны, чёрная подмесь даёт грязный тон), дефолты остаются явными ramp-значениями — но и там потребительский токен теперь будет работать.

Вердикт

Рекомендация: подход B — «как в badge»

  • «Как везде» — на самом деле зоопарк из трёх механик (аудит 2026-06-10): ~15 компонентов объявляют токены на внутреннем элементе (button, icon-button, banner, modal…) — переопределение снаружи мертво; ~10 — на :host (input, sidenav-item, card, tabs…) — работает, только если селектор консьюмера бьёт (0,1,0), голый ds-input { } и :root — нет; и лишь 4 самых новых читают с fallback (badge, tag, toast, empty-state) — единственная механика, где публичный токен работает отовсюду. Предложение — сделать её конвенцией, начав с кнопок.
  • Подход A чинить нечем: пока компонент объявляет публичный токен на своём элементе, переопределение снаружи (хост / :root / inline / !important) не работает в принципе — это правило каскада CSS. Обойти можно только селектором внутрь приватного .button с дублированием класса ради специфичности — хрупкий хак, которым консьюмеры (field, `_ds-overrides.scss`) уже вынуждены пользоваться для banner/tabs.
  • B даёт ровно вашу концепцию: из коробки само → один токен тянет полутона → любой токен точечно переписывается.
  • Визуально ничего не ломается: для primary / error / filled / selected дефолтная деривация совпадает с текущими цветами один в один; у success / warning появится чуть более тёмный pressed (сейчас он равен hover).
