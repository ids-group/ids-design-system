basic + advanced — what the split would actually buy

Refreshed 2026-09-01 — the verdict held, five later passes sharpened it

The page's own conclusion is unchanged: two packages is the wrong shape, and the numbers below still say why. What later work changed is the context around it, and the two items worth carrying into any reading of this page are:

  • The bigger prize was somewhere else entirely. One eager inject(ToastService) puts 135 744 B gzip of the library into a consumer's initial bundle — 7.0× what the table's whole directive split is worth. (An earlier draft said 5.7×, which is the ratio of the NET entry-point saving to the split, not of this gross figure; corrected 2026-09-02, and that net ratio is now 4.2×.) That is chunk placement, not component weight, and it is deck 4.
  • Breaking consumers is not a cost here. Recorded after this page was written: shipped features are free to move. So every "it would break people" argument is struck from the case against the split — what remains, and what still decides it, is the permanent mirror.

Also since: the seam overhead is a fixed 923 B rather than proportional, so the directive split keeps ~87–95% of its prize (deck 9); the CSS claim in this page's own "what survives" section was wrong and is corrected below; and the top layer of any entry-point split must be per-component. Current sources: docs/packaging-diagnosis.md, docs/packaging-chunking-audit.md, docs/todo.md.

The proposal: prototypes install a light kit, production apps add a heavy one, and ds-table is swapped for an ids-data-grid. The stated reason is bundle weight — a prototype should not drag in a large library of complex components.

Nobody had measured it. Every number below is a real production build of dist/ds 0.11.1 through a throwaway consumer workspace: same builder as a real app, optimization on, gzip. Method and reproduction in docs/basic-advanced-split-audit.md. Nothing here is an estimate.

Both premises fail. Going from the 44 components a prototype actually uses to all 96 costs 18 KB gzip — that is the entire size of the problem the split is meant to solve. And every feature named for ids-data-grid already ships in ds-table, most of it since 0.6.3. A split would not add capability; it would move shipped features into a second package and buy at most 32 KB for a table we then have to maintain twice.

The three numbers that decide it

5.6 KB Entry cost. Importing the library and using one trivial component. There is no fat always-shipped runtime.
18.2 KB The whole problem. What the 52 components a prototype never touches cost it today. Tree-shaking already removes them.
32.0 KB The table's real price beside the rest of the kit — not the 118.2 KB it shows alone. Best case for the split, and only for an app with no table.

The isolation figure is 3.7× too high because it bills the table for ds-button, ds-menu, ds-popover, ds-pagination, ds-skeleton, ds-loading-overlay and the icon set — which the rest of the app was paying for anyway. That is the number the whole proposal rests on, and it is an artefact of measuring one part in isolation.

Styles tree-shake too. Every build above emitted 0 bytes of CSS: Angular inlines component styles into the component definition, so they are dropped with the component. The only fixed style cost is the global sheet — tokens, palette, theme activation, typography, resets — at 10.3 KB gzip, which every consumer pays and no packaging change reduces.

Why it works: the preconditions are all met

  • "sideEffects": false is set, in the repo and in the published package.
  • ng-packagr emits one ESM module; the Angular compiler marks every definition /*#__PURE__*/, so an unreferenced class is dead code.
  • No third-party runtime dependency beyond tslib. @angular/cdk is a peer, and only overlay, portal and one drag-drop import are used.
  • Nothing is on by default — though not all of them are input(false): six use input<boolean | null>(null) or model(), and resolve to off anyway.

What the split would cost

  • Two tables to keep in lockstep. An advanced table cannot be a clean subclass — it needs the base table's layout machinery, its SCSS, its popover/menu/pagination internals. This is the divergence risk already raised in the thread.
  • A swap at the worst possible moment. "swap table for data grid" turns prototype → production into a template rewrite that has to be redone by hand every time a prototype graduates — the one step where the design is supposed to survive untouched.
  • A doubled release pipeline (cut → publish → deploy-docs), a doubled version matrix, and a docs site explaining two tables that look identical.
  • Return: ≤32 KB gzip, and only for apps with no table at all.

Not on that list: breaking current consumers. This library ships breaking changes freely, and a feature sitting in the wrong place is always allowed to move. The case against the split is the duplicate-maintenance burden and the size of the prize — nothing else.

The packaging problem we do have is a different one

docs/packaging-chunking-audit.md: one entry point means one module, and a module is the bundler's atom. The moment an eager graph touches one DS symbol — a root provider binding to ToastService, say — the chunk carrying every DS symbol the app uses anywhere becomes a static import of main. mm-broker measured 632 kB, 88% of a 720 kB initial bundle, in an app where every feature route is lazy.

Tree-shaking and chunk placement are orthogonal, and only placement is broken. A basic/advanced split does not fix it — ids-basic would be one entry point behaving exactly the same way. The fix is layered entry points, tracked separately and deliberately deferred; nothing is blocked on it.

What survives from the idea

The instinct — "the prototype should not carry grid machinery it never switches on" — is sound. It just does not need a second package. The table's opt-in behaviours can move into separately importable directives:

  • DsTableResizable, DsTableReorderable, DsTableExport, DsTableColumnFilters, DsTablePersistLayout — imported only where used.
  • One component, one docs page, no mirror to keep in sync, and the heavy parts tree-shake per feature instead of per package.

Measured, not assumed. The data-grid features were deleted from ds-table on a probe branch — 1 063 source lines across .ts, .html and .scss — and the same ladder re-run on the rebuilt library.

The catch the ablation exposed. The features are not cleanly separable today: clipWidth/fitsContent serve both truncate and resize, orderedColumns/visibleColumns are the computed chain the picker writes to, filteredData folds the set filters into the substring search, and statusMessage folds export state into the live region. The split needs a seam — most likely a small internal layout/state service the directives write into and the table reads — not a method-by-method move. That design work is the real cost, and it is bounded and one-off.

When a separate package is justified

Not by component count, and not by the weight of first-party code — by an external runtime dependency. A charting package pulling a charting library, or a grid pulling ag-grid, adds weight tree-shaking cannot claw back and a peer-dependency surface the design system should not own.
