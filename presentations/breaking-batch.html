The breaking batch

Everything here changes what a component does out of the box. Shipping them one release at a time surprises a consumer three times with the same class of change, so they go together or not at all. Decide each row; the migration guide writes itself from the verdicts.

It is three members, not four. The batch item lists packaging as “(d) option D, if that is the packaging answer” — it is not. A · ds-modal — a boolean where the rest of the library has a vocabulary shipped 2026-08-12 · tinted

Was: error = input(false). Everywhere else the API-consistency pass (2026-07-09) settled on DsStatus. A boolean cannot express a warning or an info dialog at all, so both consumer apps hand-roll one. What the rename actually buys — all four, in the chosen treatment

A boolean has one state. DsStatus is 'info' | 'success' | 'warning' | 'error', and each paints from the same family ds-alert reads, so a status dialog and a status alert on one screen cannot disagree with each other.

status="error"
Delete this policy
This cannot be undone.
status="warning"

status="success"

Documents are on their way to the holder.
status="info"
Scheduled maintenance
Claims search is read-only until 02:00.

The migration is one attribute per dialog, and the two boolean forms both have an exact replacement — nothing needs a judgement call:

- <ds-modal [error]="true"  title="Delete this policy">
+ <ds-modal status="error" title="Delete this policy">

- <ds-modal [error]="isDangerous">
+ <ds-modal [status]="isDangerous ? 'error' : null">

Unset stays neutral — a plain dialog is still the default, so a screen that never used error sees nothing change. ds-modal-card takes the same input, since a ModalService confirm renders one directly.

Two questions:
  1. error: boolean → status: DsStatus? Recommend yes — it is the vocabulary everywhere else, and warning/info become expressible.
  2. Which treatment? Recommend the tinted header: it reuses the idiom the library already has instead of inventing a stripe that exists nowhere else.

B · chip overflow — cap by width by default shipped 2026-08-12 · default is “fit”

maxVisibleChips used to default to “show everything”, so a multi-value trigger grew a line per selection and pushed the form down the page. "fit" shipped 2026-08-11 as an opt-in and is now the default for ds-autocomplete and ds-multi-select: [maxVisibleChips]="null" restores the growth, a NUMBER still caps at exactly that many.

Flip the default to "fit"? Recommend yes. The cost is that a screen relying on the growth sees its trigger stop growing; the fix is one word — [maxVisibleChips]="null". The benefit is that no form is pushed down the page by a selection the user made three clicks ago.

C · four defaults a consumer changed — and how each landed

These four overrides came out identical in two apps. Every one is already retunable, so the question was never “add a knob” but “is our default the wrong one”. The panels below are the proposal as filed; the verdicts follow.

Researched 2026-08-12, and the premise did not hold. The backlog called these “two independently-built apps”. They are not: both override files live in ONE repository — mm-broker-platform/…/broker-portal and …/platform-admin — two portals of the same product, and both page-header comments say the same words, “H2 to match the design”. So this is one design spec's opinion, not two teams converging, which is a much weaker argument for moving a library's default. The second consumer (mm-ecm) is not on this machine, so it could not be checked. Outcome: C1, C2 and C3 close with no default change; C4 is parked as its own item.

Where each one landed — decided 2026-08-12. Three closed with no default change; one parked.
  1. C1 — closed, 28px stays. The heading LEVEL was never wrong: the component already renders <h1 class="title">, so “h3” names a type RUNG, and the “nothing larger sits above it, so it is under-sized by construction” argument dissolves. On the rung, 28px is Material 3's Headline Medium and Apple's Title 1 — the canonical app-page-title size — while 36px is M3's Display Small, the expressive rung for one-off hero moments, not for a header that repeats on every page (Shopify Polaris, the closest analogue, goes lower still). --ds-page-header-title-fs stays the lever; its token description now names the rung and the reason.
  2. C2 — closed, and both halves were already answered. --text-tertiary on --surface-secondary measures 4.30:1 at 12px bold — normal text by WCAG, so the floor is 4.5 and a library cannot default below it. Their second declaration, --ds-table-head-bg-color: var(--surface-secondary), is a no-op re-stating our own default. And the “matching row hover” appears in neither file — while the DS already does the asked-for thing: the row tint is tr.clickable:not(.active):hover, gated by rowInteractive, off by default, so a passive table stays static and the tint honestly signals clickability.
  3. C3 — closed on the value, and it exposed a real gap that is now fixed. The padding was never ds-stat's to move: it resolves from --ds-container-pad, which ds-card shares, so hard-coding --space-5 into the tile would have removed the shared knob. On the value, 24px is where the field sits (Ant card body 24, shadcn p-6 24) and 20px is not a canonical rung anywhere — so the base stays and a consumer who wants 20 sets that one token. What did move: the density tiers compressed field and table padding at ultra-compact but left surface padding at 24px, so a card kept its full frame while its own cells halved. ultra-compact now drops it to 16px — one rung, not two, because a frame reads as padding lost long before cells do.
  4. C4 — deliberately parked (Stas 2026-08-12), now its own board item. Worth carrying into that discussion: both apps also set --ds-sidenav-item-label-weight: bold, a fifth override this item never counted, and their colours DIFFER — one uses its own --nav-active-bg, the other --primary-subtitle. They agreed on a shape, not a value.
The one thing worth keeping from the whole group.

A consumer override is evidence about a default only when it is genuinely independent. Four identical declarations inside one Angular workspace are one opinion written twice — and both page-header comments say the same words, “H2 to match the design”, which points at a single design spec rather than at two teams agreeing. Check the repository before counting the overrides. What the group did produce is real, just smaller than it looked: one contrast floor confirmed, one density gap found and fixed, and two token descriptions that now say which rung they sit on and why.

What a “yes” costs

Every verdict above lands in one release with one migration entry each: a decision rule, the exact tokens or inputs to set to keep today's look, and a search hint. Nothing here needs a consumer to rewrite markup — the escape from each is a single token or a single input.

Sources for every “now” panel: the component's own resolver defaults, read 2026-08-12 — --ds-page-header-title-fs → --font-size-h3, --ds-table-head-text-color → --text-secondary on --surface-secondary, --ds-stat-pad → --ds-container-pad (--space-6), --ds-sidenav-item-bg-color-active → --accent with --ds-sidenav-item-rail → --secondary.
