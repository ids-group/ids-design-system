The breaking batch

Everything here changes what a component does out of the box. Shipping them one release at a time surprises a consumer three times with the same class of change, so they go together or not at all. Decide each row; the migration guide writes itself from the verdicts.

It is three members, not four. The batch item lists packaging as “(d) option D, if that is the packaging answer” — it is not. Option B was decided on 2026-08-05 (one services entry point, root public-api.ts kept as a facade), and B is additive: nothing a consumer imports today stops working. It leaves the batch.

A · ds-modal — a boolean where the rest of the library has a vocabulary

Today: error = input(false). Everywhere else the API-consistency pass (2026-07-09) settled on DsStatus. A boolean cannot express a warning or an info dialog at all, so both consumer apps hand-roll one. The rename is mechanical — but it forces a second decision the rename alone does not answer: what a status modal should LOOK like. The DS has no stripe idiom anywhere; ds-alert expresses status as a tinted surface.

What the rename actually buys — all four, in the chosen treatment

A boolean has one state. DsStatus is 'info' | 'success' | 'warning' | 'error', and each paints from the same family ds-alert reads, so a status dialog and a status alert on one screen cannot disagree with each other.

status="error"
Delete this policy
This cannot be undone.
status="warning"

status="success"

Documents are on their way to the holder.
status="info"
Scheduled maintenance
Claims search is read-only until 02:00.

The migration is one attribute per dialog, and the two boolean forms both have an exact replacement — nothing needs a judgement call:

- <ds-modal [error]="true"  title="Delete this policy">
+ <ds-modal status="error" title="Delete this policy">

- <ds-modal [error]="isDangerous">
+ <ds-modal [status]="isDangerous ? 'error' : null">

Unset stays neutral — a plain dialog is still the default, so a screen that never used error sees nothing change. ds-modal-card takes the same input, since a ModalService confirm renders one directly.

Two questions:
  1. error: boolean → status: DsStatus? Recommend yes — it is the vocabulary everywhere else, and warning/info become expressible.
  2. Which treatment? Recommend the tinted header: it reuses the idiom the library already has instead of inventing a stripe that exists nowhere else.

B · chip overflow — cap by width by default

maxVisibleChips defaults to “show everything”, so a multi-value trigger grows a line per selection and pushes the form down the page. "fit" shipped 2026-08-11 as an opt-in; the question is whether it becomes the default for ds-autocomplete and ds-multi-select.

Flip the default to "fit"? Recommend yes. The cost is that a screen relying on the growth sees its trigger stop growing; the fix is one word — [maxVisibleChips]="null". The benefit is that no form is pushed down the page by a selection the user made three clicks ago.

C · four defaults two teams changed independently

These four overrides came out identical in two apps. Every one is already retunable, so the question is not “add a knob” but “is our default the wrong one”.

Researched 2026-08-12, and the premise weakened. The backlog called these “two independently-built apps”. They are not: both override files live in ONE repository — mm-broker-platform/…/broker-portal and …/platform-admin — two portals of the same product, almost certainly one design. The second consumer (mm-ecm) is not on this machine, so it could not be checked. What looked like two teams converging is one design's opinion, which is a much weaker argument for moving a library's default. Two of the four now decide themselves anyway:

Where each one landed.
  1. C2 — disqualified, and not on taste. --text-tertiary on --surface-secondary measures 4.30:1, and the head renders at 12px bold — normal text by WCAG, so the floor is 4.5. A library cannot default to a contrast failure; an app may choose it for itself. Two corrections while measuring: their second declaration, --ds-table-head-bg-color: var(--surface-secondary), is a no-op that re-states our own default, and the “matching row hover” this item claimed appears in neither file. One real declaration, and it fails.
  2. C3 — must not move alone. ds-card and ds-stat both fall back to the same semantic token, --ds-container-pad. Hard-coding --space-5 into the tile would not just break the shared rhythm — it would remove the shared knob, so an app tuning --ds-container-pad would stop moving the tile. Carbon and Atlassian both keep a core scale of 5–8 values plus a semantic per-component token, which is exactly what we have. Either move --ds-container-pad (card + stat + container together, its own decision) or leave it.
  3. C1 — still open, and closer than it looked. The element is already an <h1>; only its SIZE is at issue, 28px against the proposed 36px (+29%). 28px sits inside the productive-UI norm, so our default is defensible — the case for moving rests on the consumer evidence, which is now one design rather than two.
  4. C4 — deliberately parked (Stas 2026-08-12), to be discussed on its own. Worth carrying into that discussion: both apps also set --ds-sidenav-item-label-weight: bold, a fifth override this item never counted, and their colours DIFFER — one uses its own --nav-active-bg, the other --primary-subtitle. They agreed on a shape, not a value.

What a “yes” costs

Every verdict above lands in one release with one migration entry each: a decision rule, the exact tokens or inputs to set to keep today's look, and a search hint. Nothing here needs a consumer to rewrite markup — the escape from each is a single token or a single input.

Sources for every “now” panel: the component's own resolver defaults, read 2026-08-12 — --ds-page-header-title-fs → --font-size-h3, --ds-table-head-text-color → --text-secondary on --surface-secondary, --ds-stat-pad → --ds-container-pad (--space-6), --ds-sidenav-item-bg-color-active → --accent with --ds-sidenav-item-rail → --secondary.
