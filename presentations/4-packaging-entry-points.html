MBP-133 — one entry point, and the four ways out

Status: deferred by decision (2026-08-21), deck for when it is picked up. Every number here is from docs/packaging-chunking-audit.md — measured, either in the consumer's build or in controlled esbuild 0.27.3 fixtures. Nothing on this page is an estimate.

Correction, 2026-09-01: this deck's recommendation is dead

The page below recommends “B, and only B”. Option B is not buildable. ng-packagr forbids cycles between entry points, and a services entry point has to own button/icon/spinner, which every other component also needs — so the cycle is structural, not an accident of the current imports. Read the rest of the page as the mechanism and the measurements, which still hold; do not read the verdict.

What replaced it. A0 measured chunk placement against the real library instead of a synthetic fixture (docs/packaging-chunking-audit.md §11, docs/packaging-diagnosis.md). One inject(ToastService) adds 135 744 B gzip to the initial bundle, against a DS-free floor of 59 019 B, and collapses the lazy chunk from 566 761 to 189 bytes raw. The import graph does partition: a 13-group core that closes over itself, the services closing over 11, and a 64-group component layer on top.

The saving depends on the SHAPE, and this is the trap. The −80% figure is the eager-services case AND it needs per-component entry points. A three-layer core/services/components split does not deliver it: an eager app shell touches the component layer and pulls the whole retained layer straight back into the initial bundle. Measured on a purpose-built fixture — one components entry gives 178 538 B initial with both lazy-only components inside it; per-component entries give 125 651 B with neither. For an eager-shell consumer the honest number is 142.3 → 42.1 KB gzip, −70%.

Three cycles, and one of them is a constraint rather than work. radio↔radio-group and time-columns↔time-picker are sibling cycles. The four-way one (components/card, config, core, icons) was priced and declined — 593 B gzip to leave it alone against 40 import rewrites to break it (A3-pre DECLINED, d6b52890). So ds-card simply lives in the core entry.

D is cheaper than §7 says. Keeping the root as a pure re-export facade means no consumer changes an import — measured byte-identical down to the chunk hash at 61 entry points. One exception a consumer must be told about: a @defer block whose component is imported through the facade defers nothing at all (angular/angular#52554), so inside @defer the deep specifier is required.

One claim on this page is superseded — the reproducibility one, not the figures. The audit's §2 line said the consumer's report was not reproducible from artifacts on disk. It has since been independently reproduced on our own library, same order of magnitude: 577 kB of a 755 kB initial, 76%. Their 632 kB / 88% remains their number for their app, which has a different component set.

The mechanism, in one paragraph

ng-package.json declares a single entryFile, so the package ships as one 1.25 MB FESM behind a single "." export. Tree-shaking works — unused components are dropped, verified twice. What cannot happen is chunk placement: esbuild splits by MODULE, and one FESM is one module, so it can never put two DS symbols in two different chunks. The moment an eager graph touches one symbol, the chunk carrying every DS symbol the app uses anywhere becomes a static import of main.

In mm-broker that one symbol is a service: provideCommon → NotificationService → ToastNotificationService → ToastService. Result: 632 kB of a 720 kB initial bundle — 88% — in an app where every feature route is lazy.

Two claims in the original filing are wrong, and the audit says so. It was never a tree-shaking failure (nobody upstream claimed it was), and "the consumer has no lever" is false — a dynamic import() in the eager root keeps main clean. It just costs tree-shaking, measured below. Also: this was never filed upstream as an ask; it is the consumer's own backlog item with a consumer-side fix available.

Variant C is the consumer-side lever, and its cost is visible in the yellow: making the module a dynamic-import target turns it into an entry point, so unused exports can no longer be dropped. neverUsed-payload reappears at 400 hits and the chunk grows 40.1 → 60.6 kb, +50%. At library scale that is the difference between deferring the ~632 kB retained set and deferring the whole 1.25 MB FESM.

Recommendation, rewritten 2026-09-01: D, and the top layer must be PER-COMPONENT. The original text recommended B; B is not buildable. A first rewrite of this block said “layered rather than per-component”, and that was wrong in the expensive direction — it is corrected here.

  • With B gone the live choice is A (nothing) or D. C keeps its own disqualifier — it loses tree-shaking, measured at +50% on the deferred chunk, and every consumer has to rediscover it.
  • Three layers is not enough. A single components entry leaves an eager shell pulling the whole retained component layer back in: 178 538 B initial with both lazy-only components inside it, against 125 651 B per-component with neither. The layering (13-group core ← services ← 64 components) is the structure; the per-component split is what actually moves the bytes.
  • D is no longer priced as “85 component folders that move every consumer's imports”. A root kept as a pure re-export facade is byte-identical at 61 entry points, so no consumer changes an import — except inside @defer, which needs the deep specifier.
  • The prize, stated against the shape that delivers it: −80% for the eager-services case with per-component entries, −70% (142.3 → 42.1 KB gzip) for an eager-shell consumer.
  • Not a major on the API surface — the facade means no consumer rewrites an import, and there is no rename, no moved symbol and no changed class member. One vector is untested: a consumer on legacy moduleResolution: "node" does not read the exports map, so it cannot resolve subpath exports at all, and this package ships no typesVersions (checked: zero occurrences in the repo root and in dist/ds). Verify that before promising a non-breaking upgrade — it is the shape of defect that surfaces as “we upgraded and the build broke”.

What would change this: a measurement of the real per-component cut coming in worse than the fixture predicts. The four-way ds-config.ts cycle is no longer a risk — it was priced and declined, and ds-card lives in the core entry as a result.
