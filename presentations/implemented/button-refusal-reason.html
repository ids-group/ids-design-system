Причина отказа на кнопке

Кнопка выключена, и приложение обязано сказать почему.

Проблема. Сегодня причина живёт в тултипе: чтобы её узнать, надо навести мышь. С клавиатуры и с тача — никак. На экране не написано ничего.
Решено — причина ВНУТРИ кнопки: новый вход disabledReason. Длина не ограничена, текст переносится, обе строки по центру. DS ставит aria-disabled вместо disabled и глушит клик. Имя уже занято тем же смыслом у TableRowAction. 
<ds-button [disabled]="true" disabledReason="Нет прав">Отправить заново</ds-button>
Нужно твоё решение

Строка ПОД кнопкой — кто её рисует

Это второй, временный флоу: форма не заполнена, кнопку не гасим, причина живёт под ней. Вопрос только в том, чей это код.

1 — кнопка остаётся кнопкой

Консьюмер сам ставит ds-field-message

<ds-button (clicked)="save()"
  [ariaDescribedBy]="msgId">Сохранить</ds-button>
<ds-field-message [text]="formError()"
  [messageId]="msgId" [reserve]="true" />

Компонент уже умеет всё: text, state, icon, messageId, reserve. Добавить надо только ariaDescribedBy на кнопку — сегодня его нет.

Плюс: кнопка остаётся inline-flex, тулбар и группа кнопок не меняются.
Минус: две строки вместо одной, связь через id — консьюмер может забыть.

2 — кнопка как поле

Зеркалим API поля: hint / error / warning

<ds-button (clicked)="save()"
  [error]="formError()"
  [reserveMessage]="true">Сохранить</ds-button>

Те же входы, что у полей, и тот же резолвер resolveFieldMessage — он уже решает, какое сообщение победило, и отдаёт severity. Связь aria-describedby кнопка проставляет сама.

Плюс: одна строка в шаблоне, забыть связь невозможно.
Минус: кнопка становится «полем» — хост придётся делать блоком, когда сообщение задано. И DS сознательно держал эти входы только у полей.

Замечание к варианту 2: success в базу полей намеренно не поднят («иначе чекбокс получит success, а слайдер label»), так что зеркалить стоит ровно три — hint, warning, error.
