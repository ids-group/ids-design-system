Entry-point shape — three layouts, built

Deck 5 recommends option D with a per-component top layer, and the numbers behind it are settled. This is the sub-question that has to be answered before a line of it can be written, and it was not in the plan: what will the specifiers actually look like, and what does the library's folder layout have to become to get there.

The constraint that forces the question. An entry point's public specifier is the directory path relative to the package root, verbatim. There is no option to name an entry point — verified against all eight keys of the installed ng-package.schema.json, and confirmed by building a deliberately nested entry: a folder at deep/nested published as probelib/deep/nested with a FESM called probelib-deep-nested.mjs.

Our ng-package.json sits at the repo root and our sources live under src/lib/. So doing nothing about the layout gives specifiers like @ids-group-ltd/ids-design-system/src/lib/components/button.

Three layouts, each built for real

Prototypes at .claude/local/shape-probe/ — three libraries with the same content (a core plus two components), differing only in where the package root sits and how deep the component folders are. All three built cleanly with ng-packagr; the maps below are copied from the exports field each build actually emitted.

The 307 rewrites are the same number in all three, which is the thing that makes C cheaper than it first appears. An import that becomes a public specifier does not care how deep its file sits, so the 145 imports inside component folders that reach above components/ get rewritten once either way. C's genuinely extra work is 71 folder moves — mechanical git mv — plus finding a home for the 23 loose files that would otherwise collide at src/lib/, plus fixing depth on the intra-core relative imports that stay relative.

The version trap, and it applies to B and C equally

Today there is one package.json, at the repo root. It holds the version, npm version bumps it, and ng-packagr copies that number into the published package. One file, one source of truth.

Move the package root to src/lib/ and ng-packagr stops reading the root package.json — it reads src/lib/package.json instead. Two files now carry a version. infrastructure/scripts/cut-release.sh:75 still reads ./package.json, so a release would bump one file and publish the number from the other. Silently wrong version on npm.

Two ways out, and this only needs deciding if B or C wins:

  • Generate src/lib/package.json from the root one in a prebuild step. One source of truth stays where it is, npm version and cut-release.sh do not change at all. The repo already generates committed files this way (tokens.generated.ts, component-api.generated.ts).
  • Move the version's home to src/lib/package.json and point cut-release.sh and npm version at it. Conceptually cleaner, but it edits a release chain that took real work to get right.

Recommendation

B, with the generated package.json. It buys readable specifiers for the price of moving one file, and it leaves the release pipeline untouched. components/ in the path is mildly verbose and completely harmless — it is also honest about where the source lives.

C is the one to pick if the specifier matters more than the diff, and it is defensible: it is what Angular Material and @angular/cdk publish, the specifier is what consumers read for years, and the extra churn is 71 git mvs rather than a second wave of import rewrites. What it costs is a flat src/lib/ holding roughly ninety entries, and a decision about where the 23 loose files go.
