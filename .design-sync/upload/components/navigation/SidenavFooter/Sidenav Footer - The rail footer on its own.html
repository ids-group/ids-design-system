Sidenav Footer - the rail footer on its own

<SidenavFooter />

<ds-sidenav-footer> is the one part of the rail a consumer configures rather than composes: it owns the profile row, the alert bell and the collapse handle. Both states below are the same element — [collapsed] switches it. The width comes from the sidenav, so a footer shown outside one needs a frame of its own.

Emits the new path whenever navigation lands on a DIFFERENT one. A query- or fragment-only navigation is a search, sort or page step on the same screen, and everything that reacts to "went somewhere else" must agree on that — the scroll reset, the responsive rail, and now your own code — so they read one source instead of each deciding for itself. PUBLIC since 0.8.x, because consumers were re-deriving it and disagreeing: one consumer had three separate answers to "did the path change?" — route snapshots in a view-transition skip, this stream inside the layout, and a `split('?')` in a tab helper that ignored the fragment this one strips. Inject it and read `pathChanged` rather than writing a fourth: ```ts private readonly navigation = inject(LayoutNavigationService); constructor() { this.navigation.pathChanged .pipe(takeUntilDestroyed()) .subscribe((path) => …); } ``` A PATH change is not always a page change. An app whose URL mirrors the reader's position — a docs layout rewriting `/area/section` from a scroll spy, a wizard that names its step — changes the path while staying on the screen, and resetting the scroll there fights the user: the reset moves the scroll, the spy rewrites the path again, and the page ping-pongs. Such a navigation must carry `state: { dsSamePage: true }`, which is skipped here. Root-provided, which is also what makes it safe to expose: the stream is derived from the router and holds no state, so one instance serves every reader. `LayoutScrollService` depends on it, so a consumer providing THAT outside `ds-app-layout` needs this one resolvable too.

LayoutNavigationService properties 1
Name Type Description
pathChanged Observable<string> Emits the new path on every navigation that lands on a DIFFERENT path — query and hash are stripped, repeats are dropped, and a navigation the app marked `dsSamePage` is skipped entirely.

Owns the layout's content scroller. In the fixed-frame layout the window never scrolls, so the router's built-in window-based scrolling no-ops — this service resets the registered container to the top when navigation lands on a different PATH instead. Provided by `ds-app-layout`, so routed pages can `inject(LayoutScrollService)` and call `scrollToTop()` manually (e.g. list pages that DO want the top after a filter change). With `restoreScroll` on the layout it also restores the reader's place. Only when ARMED, which is the whole design: going BACK to a list should return to where the reader was, while following a link into a new screen should not.

LayoutScrollService methods 7
Signature Returns Description
setScrollContainer(element: Element) void Wiring, called by `ds-app-layout` once its content region exists. Public only because the component and the service sit in different files - a consumer has no reason to call it, and calling it points the service at the wrong element.
configureRestore(timeoutMs: number | null) void Wiring: `ds-app-layout` mirrors its `restoreScroll` inputs through here.
configureReset(strategy: DsScrollReset) void Wiring: `ds-app-layout` mirrors its `scrollReset` input through here.
scrollToTop() void Send the layout's content region back to the top. For a screen that wants the top after its own filter or sort change, which `resetScroll="path"` deliberately does not do.
scrollTo(top: number) void Scroll the content region to an absolute offset. Assigns `scrollTop` rather than calling `scrollTo`, so a themed `scroll-behavior: smooth` cannot turn a positioning jump into an animation.
consumePendingOffset() number | null Take the offset this navigation is going to restore, and cancel the restore. For a host that renders its own scroll position — a virtualizer needs the offset BEFORE it decides which rows to build, so letting the service assign `scrollTop` afterwards would scroll a list that has not been built yet. Returns null when nothing is pending, which is every navigation that is not a back.
contentReady() void Optional accelerator: tell the layout the content for this route is in the DOM. Without it the restore still lands — it waits for the container to grow and clamps at the deadline — but a host that knows when its data arrived can end the wait early instead of paying the growth watch.
