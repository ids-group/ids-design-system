App layout - content-span topbar

<AppLayout />

The fixed application frame: the rail and topbar stay pinned while only the content region scrolls. Consumers project their own chrome into the [sidenav] , [topbar] and default slots — the layout renders the <main> landmark and compensates the scrollbar so the content insets stay symmetric.

Default geometry — the rail spans the full height on the left and the topbar sits above the content column only. Scroll the filler: the rail and topbar hold their place. The footer's Search and Alerts rows open live popovers, and opening Alerts clears the unread dot.

Inputs 6
Name Type Default Description
topbarSpan content full 'content' `'content'` (default): the rail spans the full viewport height on the left and the topbar sits above the content column only. `'full'`: the topbar spans the full width and the rail + content sit below it.
railOpen two-way boolean false Whether the rail is open as an overlay. Only meaningful below the `lg` breakpoint — above it the rail is always in the layout and this is ignored. Two-way, so a burger in your topbar can drive it.
railLabel string 'Navigation' Accessible name for the rail while it is a modal overlay.
restoreScroll boolean false Remember the content scroll per path and restore it on the way BACK. Off by default: a layout that silently moved the scroll would surprise every existing consumer. Only a history traversal restores — following a link into a screen still lands at the top — plus a host that pushes its own "back to list" and says so with `state: { dsRestoreScroll: true }`, and the first navigation after a reload.
restoreScrollTimeout number 2000 How long to wait for the restored screen's content to grow tall enough before landing as close as it allows. Only meaningful with `restoreScroll`.
scrollReset path never always 'path' When the content scroll resets to the top. `'path'` (default) is what the layout has always done; `'always'` also resets on a query- or fragment-only navigation, which is what a server-paged list wants; `'never'` hands the decision to the screen, which can still call `LayoutScrollService.scrollToTop()`. It exists because the layout owning the scroll CONTAINER also meant it owned the POLICY: a screen could add a reset but had no way to suppress one.
