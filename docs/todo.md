## From mm-ecm agent-portal migration (2026-07-31)

Dogfooding source: migrating the **NYL "refresh" editorial design** (square corners, chamfered cards, uppercase tracked labels, weight-driven states) in `mm-ecm/prototype/projects/agent-portal` off hand-rolled markup onto DS **0.7.0** — `ds-table`, `ds-modal`, `ds-badge`, `ds-button`, `ds-select`, `ds-input`, `ds-textarea`, `ds-checkbox`, `ds-radio-group`, `ds-date-picker`, `ds-time-picker`. Every item below is something the consumer could only solve with **global CSS against DS-internal class names**, using doubled/tripled class selectors (or `!important`) to out-rank the encapsulation shim; all the workarounds sit in one commented block in that portal's `styles.scss`.

**Status 2026-07-31:** 7 of the 11 original items SHIPPED the same day (option-hover specificity · modal eyebrow/title-size/empty-footer · table asymmetric padding + header tokens · table `rowId` · pagination label tokens + `showPageSize` · `reserveMessage` via `DS_CONFIG` · checkbox/panel radius), plus parts (c) and (d) of the picker item — all archived in `done.md`. The four below stayed because each needs a decision from Stas: a breaking rename, a change to a DEFAULT look, or an approach call.

**Provenance caveat:** all claims read out of the **compiled 0.7.0 bundle** (`fesm2022/*.mjs` + `types/*.d.ts`) as installed in the consumer, NOT from `src/lib` — selectors, class names and token names are exact, but re-confirm file:line at fix time per [[feedback-validate-before-applying]].

- [ ] **[P1] Field labels have THREE different contracts across the field family — `--ds-input-label-*` styles exactly one component.** `ds-input` reads `--ds-input-label-fs`/`-fw`/`-color` ✅; `ds-textarea` + `ds-date-picker` hard-code `font: var(--font-weight-bold) var(--font-size-xs)/… var(--font-sans)` + `--text-secondary` with NO hooks; `ds-select` hard-codes the same **and names its element `.select-label`** instead of `.label`; `ds-checkbox` uses `.control-text` + internal `--_checkbox-label-fs`. Consequence: any form mixing select + input renders labels in two sizes/colours out of the box, and a consumer retune needs `.field.field .label.label, .select-label.select-label` (the `.field` doubling only because the shimmed DS rule is `.field[_ngcontent] .label[_ngcontent]` = (0,4,0)). **Ask:** one shared label partial, ONE class name across the family, one token set — `--ds-field-label-fs`/`-fw`/`-color` **plus `-transform` and `-tracking`** (uppercase tracked labels are a common editorial pattern, currently unreachable through tokens). Same consumer-first `--ds-*` principle as the `.t-*` hooks item — spec together.
- [ ] **[P1] `ds-date-picker` and `ds-time-picker` disagree with each other and with the input family.** Four mismatches, all visible when the two sit in one form row: (a) **value typography** — date pins `font-family: var(--font-mono)` on `.date-input` (the value reads as a mask), time uses `--font-sans` + `--font-weight-medium`, input/select use sans regular = three fonts in one row; (b) **glyph order** — time renders `ds-icon[name=clock]` BEFORE `.time-value`, date renders value-then-calendar, so they mirror each other; (c) **radius** — DONE 2026-07-31, `--ds-date-picker-trigger-radius` added; (d) **width** — DONE 2026-07-31, opt-in `fullWidth` on both pickers (host class stretches the trigger, and for time also the wrap + range row); default stays hug-content. REMAINING in this item: (a) value typography and (b) glyph order — both change the DEFAULT look, so they need a design call. **Ask:** `--ds-date-picker-trigger-radius`; `--ds-*-value-fs`/`-fw`/`-family` (or inherit the field family); a `fullWidth`/block mode; matching glyph order (or an `iconPosition` input).
- [ ] **[P2] Control height is computed two different ways across the field family.** `ds-input`/`ds-select` are padding-driven (`--_input-pad-y`, `--field-pad-*`); both pickers are fixed `height: var(--hit-cozy)`. The same nominal `size` therefore does NOT guarantee equal box heights in one row — the consumer had to pin both picker triggers by hand. **Ask:** a shared control-box contract (`--ds-field-h`, `--ds-field-pad-x`) every field resolves through. **Pairs with the token-architecture pass.**
- [ ] **[P2] `ds-button` — no type-scale or box hooks, and per-variant tokens are unreachable from the host.** `.button` hard-codes `font: var(--font-weight-extrabold) var(--font-size-m)` + `letter-spacing: var(--letter-spacing-wide)`, and `.button.md` pins `height` + `padding` — so a brand wanting 14px/600 square buttons sized by their padding needs `.button.button.button { font-size; font-weight; letter-spacing; padding; height: auto }` (tripled class to clear the shimmed `.button.md[_ngcontent]` = (0,3,0)). Worse, variant styling lives on the **inner** `.button.v-*`, so per-variant `--ds-button-*` values can only be declared there — and a declaration on `.button` beats anything the consumer sets on the host, which forced an indirection-var layer (`--rp-btn-*`) just to keep per-instance overrides working (one banner needed white-hairline outline buttons on navy). **Ask:** `--ds-button-fs`/`-fw`/`-tracking`/`-h`/`-pad-x`/`-pad-y`, and either reflect `variant`/`color` as host attributes (`[attr.data-variant]`) or resolve variant tokens through a host-settable fallback chain.

**What the DS already got right here (keep as the pattern):** `styles/_dropdown-overlay.scss` ships the portaled option list as GLOBAL css and styles it from semantic tokens (`--primary-subtitle`, `--primary-strong`, `--surface-secondary`), so rebranding the selected row was three token retargets scoped to `.ds-dropdown-panel` — no class coupling, no specificity fight (bar the hover bug above). Same for `forwardOverlayTokens`, which copies host `--ds-*` values onto the portaled pane. Extending both patterns is the cheapest route to closing most of this section.

## Packaging — secondary entry points (optional, future)

> **Not needed for correctness — tree-shaking already works.** Verified 2026-07-27 via a linker+esbuild pseudo-build on `dist/ds`: bundle size scales with imports (Button-only < 6-component subset < whole lib), so unused components ARE dropped by a consumer's production build. Precondition holds: root `package.json` `"sideEffects": false` + 81 standalone components + ESM FESM. Consider secondary entry points ONLY if the lib grows much larger or we want guaranteed per-component chunks / lazy loading.

**What it is.** Ship the library as many small sub-packages under one name, à la `@angular/material/button`, `@angular/cdk/overlay`. Consumers import `@ids-group-ltd/ids-design-system/button` instead of the single barrel. Each entry point is its own module graph the bundler reasons about independently.

**Why (beyond what we already have).**
- Bundler-agnostic tree-shaking: even a naive/older bundler, or a consumer doing `import * as DS`, gets only the entry point it touched — no reliance on `sideEffects` + DCE being perfect.
- True lazy loading: `import('@ids-group-ltd/ids-design-system/date-picker')` splits date-picker into its own async chunk.
- Faster consumer rebuilds, clearer dependency edges.

**Current state (single entry point).** `ng-package.json` → `lib.entryFile: src/public-api.ts`; one barrel re-exports all ~74 component folders → one FESM (`dist/ds/fesm2022/…mjs`, ~1.2 MB raw). Styles ship separately as raw SCSS assets under `styles/` + `themes/` — unaffected by this change.

**What to do (ng-packagr secondary entry points).**
1. In each component folder that becomes its own entry point, add a minimal `ng-package.json` + a local `public-api.ts`. Example — `src/lib/components/button/`:
   - `ng-package.json`: `{ "lib": { "entryFile": "public-api.ts" } }`
   - `public-api.ts`: `export * from './button.component'; export type * from './button.types';`
   ng-packagr auto-discovers nested `ng-package.json` under the primary source root and emits a secondary entry point named by folder path (→ `@ids-group-ltd/ids-design-system/button`).
2. Keep the root `public-api.ts` as a **facade** re-exporting the secondary entry points, so the current barrel import keeps working — no forced breaking change; new code opts into the granular path.
3. Secondary entry points may **not** deep-import each other's internals (`../modal/modal.component`) — they must go through the sibling's public entry, or share via a `core`/`internal` entry point. ng-packagr errors on cross-entry deep imports, which is exactly what surfaces hidden coupling.
4. Shared internals (icons, overlay/portal helpers, `core/status`, config, theme) → their own entry points (`…/icons`, `…/core`) that components depend on.

**How it looks in our case.**
```ts
// today (kept working as a facade):
import { ButtonComponent, DatePickerComponent } from '@ids-group-ltd/ids-design-system';
// after (granular, opt-in):
import { ButtonComponent } from '@ids-group-ltd/ids-design-system/button';
import { DatePickerComponent } from '@ids-group-ltd/ids-design-system/date-picker';
// lazy:
const { DatePickerComponent } = await import('@ids-group-ltd/ids-design-system/date-picker');
```

**Cost / caveats.** ~74 tiny `ng-package.json` + `public-api.ts` pairs to add + maintain (scriptable via a generator); cross-entry imports must launder through public entries — a one-time refactor that also **exposes and forces fixing real coupling**; slightly longer lib build; styles/tokens layer unchanged (already asset-based).

**Verdict:** defer. Revisit if (a) component count roughly doubles, (b) a consumer needs route-level lazy loading of a heavy component (date-picker/table/color-picker/tree), or (c) we want tree-shaking guaranteed independent of consumer bundler quality.
