  1. **The doc line is false.** "Reserves space for a leading addon projected into `[dsInputPrefix]`" — it reserves nothing; `.field.with-addon .control { padding-left: 0 }` REMOVES the control's inset so a `.addon`-classed block can sit flush and take the field's corner radii. - [ ] **[P2] `dsTooltip` never opens from the keyboard on a wrapper component, and a DISABLED `ds-menu-item` / `ds-button` can never show its reason (2026-07-28, Stas — mm-broker admin users list, MBP-117 review #9).** Two defects that compound, so the "disabled + tooltip explaining why" pattern every admin AC asks for (MBP-29 AC-13/AC-14/AC-16, EC-11) is mouse-only:
  1. **`focus` does not bubble.** The directive binds `host: { '(focus)', '(blur)' }` (`tooltip.directive.ts`), but on `<ds-menu-item [dsTooltip]>` / `<ds-button [dsTooltip]>` the focusable element is the component's INNER `<button>`, and a native `focus` listener on the non-focusable host element is never called. - [ ] **[P1] `dsTooltip` leaves orphaned panels on screen forever — every collapsed `ds-sidenav` accumulates them (2026-07-28, Stas — mm-broker admin, reproduced in the browser).** Steps: collapse the rail, hover an item (tooltip shows), click it. The tooltip **stays** — and hovering the next item adds a second one, so the rail ends up wearing a stack of stale labels ("Dashboard", "Carriers & Products", … all visible at once) that nothing can dismiss. Measured: `1` panel after hover, still `1` after the click that navigated, `2` after hovering the neighbour, texts confirming both. Two independent causes, both in `tooltip.directive.ts`:
  1. **Activation never closes the tip.** The directive only listens for `mouseleave` / `blur` / `Escape`. Clicking a `ds-sidenav-item` navigates and the anchor is re-rendered under a stationary cursor, so no `mouseleave` ever arrives. Fix: close on `click`/`pointerdown` — selecting the thing the tip describes is the clearest dismiss signal there is.
  2. **`show()` overwrites `this.ref` without disposing it.** A second open (repeat `mouseenter` on a re-rendered host, or a re-entrant hover) leaks the first overlay: nothing holds a reference, so neither `onClose()` nor `ngOnDestroy()` can ever dispose it. Side evidence: the host ends up with `aria-describedby="ds-tooltip-44 ds-tooltip-44"` — the same id appended twice. Fix: dispose (or reuse) an existing `ref` at the top of `show()`, and clear the pending timer symmetrically.
  Consumer impact: cosmetic but permanent within a session, on the most-used chrome in the product. **Workaround found 2026-07-29 (mm-admin `main-layout`), and it shows how deep a consumer has to reach:** on `(mousedown)` over a rail item, `closest('a')` — the DS component's own inner anchor — gets a synthetic `mouseleave` (the directive's public close path, which disposes the tip and clears the pending timer) and the event is `preventDefault()`ed so the click never focuses the anchor, because that focus is what fires the second `show()` that orphans the first overlay. Delete it here once the directive closes on activation.
- [ ] **[P2] Collapsed `ds-sidenav` is 1px too narrow for its own items (2026-07-28, Stas — mm-broker admin, measured).** `--sidenav-w-collapsed: 64px` minus the host's `padding: var(--space-3)` on both sides (24px) minus the 1px right border leaves a **39px** content box, while `:host(.collapsed) .item` is `width: var(--sidenav-collapsed-item)` = **40px**. Every collapsed rail therefore overflows horizontally by 1px, which is invisible until a consumer puts `overflow-y: auto` on the rail for tall menus — CSS then promotes the x axis to `auto` too and a horizontal scrollbar appears under the rail, eating 17px of its height. Fix: make the geometry close (65px collapsed width, or 40px item inside 12px padding → item `width: 100%`), and consider `overflow-x: clip` on the host so a stray pixel can never scroll. mm works around it with `overflow-x: clip` on its own rail wrapper.
- [ ] **[P1] `ds-table` — cannot page against a server row count (2026-07-28, Stas — ai-sdlc starter `feat/list-screen-kit`, ADR 0017).** The pager is hard-wired to the rows in hand, so server-side paging is not expressible at all. **Verified 2026-07-28 against current source (0.6.3):** the footer renders `<ds-pagination [total]="filteredData().length">` (`table.component.html:361`) and `pagedData` re-slices by `(page() - 1) * size` (`table.component.ts:616-624`). A host that pages server-side hands the table ONE page plus the 1-based page number, and both halves misfire: `totalPages` collapses to `ceil(pageSize / pageSize) = 1`, so **every page past the first is unreachable**, and a deep link to page 2 slices `[10,20)` out of a 10-row array so the body renders **nothing** — the empty slot doesn't cover it either, being gated on `!filteredData().length` (`table.component.html:192`), which is false. **Fix:** an optional `total` input (`null` = today's `filteredData().length`); when supplied, feed it to `ds-pagination` AND skip the internal slice, since the host has already sliced. Small and non-breaking, and it settles two caveats already written into the items below/above — "when the host supplies a server row count the host owns the clamp" (paging item below) and the `totalRows` half of the lazy item (L90). **Consumer impact:** blocking — the ai-sdlc starter's list-screen kit is held at review until this lands, and that kit is the shape every new prototype copies. Its demo only looks correct because 3 mock rows never exceed one page.
- [ ] **[P2] `ds-table` — the three-state sort cycle has no opt-out, and its third click desyncs the header (2026-07-29, Stas — ai-sdlc starter list-screen kit).** `onSort` cycles asc → desc → **null** with no way to disable the null state. On a server-paged list "unsorted" is not legal (`LIMIT/OFFSET` with no `ORDER BY` repeats and skips rows), so a consumer must map null back onto its own default sort — which exposes a second defect. `onSort` runs `sortKey.set(dir ? col.key : null)` internally; a consumer binding one-way `[sortKey]` from its store sees that expression evaluate to the SAME key before and after (default column in, default column out), so Angular's binding diff skips the write and the table keeps `sortKey === null`. Result: rows are sorted, but every header shows the neutral icon and `ariaSort()` reports `'none'` — it misreports the order to sighted and screen-reader users alike, and it hits precisely the default sort column. **Fix:** a `sortingOrder`-style input so a consumer can declare `['asc','desc']` and never reach null. Every major grid ships this escape hatch — AG Grid `sortingOrder`, TanStack `enableSortingRemoval: false`, Material `matSortDisableClear`; PrimeNG's single-sort mode has no third state at all. It also removes the desync as a side effect; until then, one-way `[sortKey]` binding is quietly unreliable.
- [ ] **[P3] `ds-table` — pull the two paging behaviours out of the mm-broker fork before that fork retires (2026-07-28, Stas — mm-broker admin `ids-data-table`).** Both are generic and both are missing from `ds-table`, so every consumer that pages client-side rediscovers them: (a) **clamp an out-of-range page** — a filter that shrinks the result set leaves `page` past the end and the slice renders empty, so the table should pull `page` back to the last page that has rows (mm does this in an effect, guarded to client-side paging: when the host supplies a server row count the host owns the clamp); (b) **scroll the table into view on a page change** — paging from a pager at the bottom of a long table otherwise leaves the viewport on the last rows of the new page (`scrollIntoView({ block: 'start' })`, skipped on the first render). Both live in `ids-data-table.component.ts` today and are on mm's list to push upstream when the wrapper folds into `ds-table`.

## Packaging — secondary entry points (optional, future)

> **Not needed for correctness — tree-shaking already works.** Verified 2026-07-27 via a linker+esbuild pseudo-build on `dist/ds`: bundle size scales with imports (Button-only < 6-component subset < whole lib), so unused components ARE dropped by a consumer's production build. Precondition holds: root `package.json` `"sideEffects": false` + 81 standalone components + ESM FESM. Consider secondary entry points ONLY if the lib grows much larger or we want guaranteed per-component chunks / lazy loading.

**What it is.** Ship the library as many small sub-packages under one name, à la `@angular/material/button`, `@angular/cdk/overlay`. Consumers import `@ids-group-ltd/ids-design-system/button` instead of the single barrel. Each entry point is its own module graph the bundler reasons about independently.

**Why (beyond what we already have).**
- Bundler-agnostic tree-shaking: even a naive/older bundler, or a consumer doing `import * as DS`, gets only the entry point it touched — no reliance on `sideEffects` + DCE being perfect.
- True lazy loading: `import('@ids-group-ltd/ids-design-system/date-picker')` splits date-picker into its own async chunk.
- Faster consumer rebuilds, clearer dependency edges.

**Current state (single entry point).** `ng-package.json` → `lib.entryFile: src/public-api.ts`; one barrel re-exports all ~74 component folders → one FESM (`dist/ds/fesm2022/…mjs`, ~1.2 MB raw). Styles ship separately as raw SCSS assets under `styles/` + `themes/` — unaffected by this change.

**What to do (ng-packagr secondary entry points).**
1. In each component folder that becomes its own entry point, add a minimal `ng-package.json` + a local `public-api.ts`. Example — `src/lib/components/button/`:
   - `ng-package.json`: `{ "lib": { "entryFile": "public-api.ts" } }`
   - `public-api.ts`: `export * from './button.component'; export type * from './button.types';`
   ng-packagr auto-discovers nested `ng-package.json` under the primary source root and emits a secondary entry point named by folder path (→ `@ids-group-ltd/ids-design-system/button`).
2. Keep the root `public-api.ts` as a **facade** re-exporting the secondary entry points, so the current barrel import keeps working — no forced breaking change; new code opts into the granular path.
3. Secondary entry points may **not** deep-import each other's internals (`../modal/modal.component`) — they must go through the sibling's public entry, or share via a `core`/`internal` entry point. ng-packagr errors on cross-entry deep imports, which is exactly what surfaces hidden coupling.
4. Shared internals (icons, overlay/portal helpers, `core/status`, config, theme) → their own entry points (`…/icons`, `…/core`) that components depend on.

**How it looks in our case.**
```ts
// today (kept working as a facade):
import { ButtonComponent, DatePickerComponent } from '@ids-group-ltd/ids-design-system';
// after (granular, opt-in):
import { ButtonComponent } from '@ids-group-ltd/ids-design-system/button';
import { DatePickerComponent } from '@ids-group-ltd/ids-design-system/date-picker';
// lazy:
const { DatePickerComponent } = await import('@ids-group-ltd/ids-design-system/date-picker');
```

**Cost / caveats.** ~74 tiny `ng-package.json` + `public-api.ts` pairs to add + maintain (scriptable via a generator); cross-entry imports must launder through public entries — a one-time refactor that also **exposes and forces fixing real coupling**; slightly longer lib build; styles/tokens layer unchanged (already asset-based).

**Verdict:** defer. Revisit if (a) component count roughly doubles, (b) a consumer needs route-level lazy loading of a heavy component (date-picker/table/color-picker/tree), or (c) we want tree-shaking guaranteed independent of consumer bundler quality.
