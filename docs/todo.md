## From mm-ecm agent-portal migration (2026-07-31)

Dogfooding source: migrating the **NYL "refresh" editorial design** (square corners, chamfered cards, uppercase tracked labels, weight-driven states) in `mm-ecm/prototype/projects/agent-portal` off hand-rolled markup onto DS **0.7.0** — `ds-table`, `ds-modal`, `ds-badge`, `ds-button`, `ds-select`, `ds-input`, `ds-textarea`, `ds-checkbox`, `ds-radio-group`, `ds-date-picker`, `ds-time-picker`. Every item below is something the consumer could only solve with **global CSS against DS-internal class names**, using doubled/tripled class selectors (or `!important`) to out-rank the encapsulation shim; all the workarounds sit in one commented block in that portal's `styles.scss`.

**Status 2026-07-31:** 7 of the 11 original items SHIPPED the same day (option-hover specificity · modal eyebrow/title-size/empty-footer · table asymmetric padding + header tokens · table `rowId` · pagination label tokens + `showPageSize` · `reserveMessage` via `DS_CONFIG` · checkbox/panel radius), plus parts (c) and (d) of the picker item — all archived in `done.md`. The four below stayed because each needs a decision from Stas: a breaking rename, a change to a DEFAULT look, or an approach call.

**Provenance caveat:** all claims read out of the **compiled 0.7.0 bundle** (`fesm2022/*.mjs` + `types/*.d.ts`) as installed in the consumer, NOT from `src/lib` — selectors, class names and token names are exact, but re-confirm file:line at fix time per [[feedback-validate-before-applying]].

- [ ] **[P1] Field labels have THREE different contracts across the field family — `--ds-input-label-*` styles exactly one component.** `ds-input` reads `--ds-input-label-fs`/`-fw`/`-color` ✅; `ds-textarea` + `ds-date-picker` hard-code `font: var(--font-weight-bold) var(--font-size-xs)/… var(--font-sans)` + `--text-secondary` with NO hooks; `ds-select` hard-codes the same **and names its element `.select-label`** instead of `.label`; `ds-checkbox` uses `.control-text` + internal `--_checkbox-label-fs`. Consequence: any form mixing select + input renders labels in two sizes/colours out of the box, and a consumer retune needs `.field.field .label.label, .select-label.select-label` (the `.field` doubling only because the shimmed DS rule is `.field[_ngcontent] .label[_ngcontent]` = (0,4,0)). **Ask:** one shared label partial, ONE class name across the family, one token set — `--ds-field-label-fs`/`-fw`/`-color` **plus `-transform` and `-tracking`** (uppercase tracked labels are a common editorial pattern, currently unreachable through tokens). Same consumer-first `--ds-*` principle as the `.t-*` hooks item — spec together.
- [ ] **[P1] `ds-date-picker` and `ds-time-picker` disagree with each other and with the input family.** Four mismatches, all visible when the two sit in one form row: (a) **value typography** — date pins `font-family: var(--font-mono)` on `.date-input` (the value reads as a mask), time uses `--font-sans` + `--font-weight-medium`, input/select use sans regular = three fonts in one row; (b) **glyph order** — time renders `ds-icon[name=clock]` BEFORE `.time-value`, date renders value-then-calendar, so they mirror each other; (c) **radius** — DONE 2026-07-31, `--ds-date-picker-trigger-radius` added; (d) **width** — DONE 2026-07-31, opt-in `fullWidth` on both pickers (host class stretches the trigger, and for time also the wrap + range row); default stays hug-content. REMAINING in this item: (a) value typography and (b) glyph order — both change the DEFAULT look, so they need a design call. **Ask:** `--ds-date-picker-trigger-radius`; `--ds-*-value-fs`/`-fw`/`-family` (or inherit the field family); a `fullWidth`/block mode; matching glyph order (or an `iconPosition` input).
- [ ] **[P2] Control height is computed two different ways across the field family.** `ds-input`/`ds-select` are padding-driven (`--_input-pad-y`, `--field-pad-*`); both pickers are fixed `height: var(--hit-cozy)`. The same nominal `size` therefore does NOT guarantee equal box heights in one row — the consumer had to pin both picker triggers by hand. **Ask:** a shared control-box contract (`--ds-field-h`, `--ds-field-pad-x`) every field resolves through. **Pairs with the token-architecture pass.**
- [ ] **[P2] `ds-button` — no type-scale or box hooks, and per-variant tokens are unreachable from the host.** `.button` hard-codes `font: var(--font-weight-extrabold) var(--font-size-m)` + `letter-spacing: var(--letter-spacing-wide)`, and `.button.md` pins `height` + `padding` — so a brand wanting 14px/600 square buttons sized by their padding needs `.button.button.button { font-size; font-weight; letter-spacing; padding; height: auto }` (tripled class to clear the shimmed `.button.md[_ngcontent]` = (0,3,0)). Worse, variant styling lives on the **inner** `.button.v-*`, so per-variant `--ds-button-*` values can only be declared there — and a declaration on `.button` beats anything the consumer sets on the host, which forced an indirection-var layer (`--rp-btn-*`) just to keep per-instance overrides working (one banner needed white-hairline outline buttons on navy). **Ask:** `--ds-button-fs`/`-fw`/`-tracking`/`-h`/`-pad-x`/`-pad-y`, and either reflect `variant`/`color` as host attributes (`[attr.data-variant]`) or resolve variant tokens through a host-settable fallback chain.

**What the DS already got right here (keep as the pattern):** `styles/_dropdown-overlay.scss` ships the portaled option list as GLOBAL css and styles it from semantic tokens (`--primary-subtitle`, `--primary-strong`, `--surface-secondary`), so rebranding the selected row was three token retargets scoped to `.ds-dropdown-panel` — no class coupling, no specificity fight (bar the hover bug above). Same for `forwardOverlayTokens`, which copies host `--ds-*` values onto the portaled pane. Extending both patterns is the cheapest route to closing most of this section.

Every consumer with a money or date column hits this the moment a user clicks the header — the table looks sorted and is not, which is worse than an unsorted column. mm-broker had to subclass and override `sortedData` with a comparator that sniffs the cell text (numeric/currency/percent → parse; several date formats → `Date.parse`; blanks like `—`, `n/a`, `never` → always last regardless of direction), see its `common/components/.../data-table/display-compare.ts`. **Proposal:** either (a) a per-column `sortValue: (row) => string | number | Date` so the consumer sorts by the DOMAIN value instead of the rendered one — cleanest, and it also removes the need to re-parse what the app already had typed — or (b) a per-column `sortType: 'text' | 'number' | 'date'` with DS-owned parsing. Prefer (a); (b) is the migration-free fallback. Blank-last must hold in both directions either way. **Framing narrowed 2026-08-03 (see `packaging-chunking-audit.md` §9.4) — the ask is unchanged.** "Sorts display strings lexically" is not true across the board: `sortedData` tries a numeric fast path first, `NUMERIC = /^-?\d+(\.\d+)?$/` at `table.component.ts:44`, used at `:632-641`. So a column of bare `1234` values already sorts correctly, and the defect is scoped to **formatted** values — currency, `%`, thousands separators, dates — which is exactly what the consumer's `display-compare.ts` parses. Keeps this a P1 (money and date columns are the common case), but a consumer with plain numbers is not affected, so the blast radius is smaller than the original report implies.
- [ ] **[P2] `ds-table` `clientSort` defaults to `false`, so `sortable: true` columns render DEAD headers (2026-07-31, Stas — mm-broker MBP-133).** Marking a column `sortable: true` draws the affordance — the header looks clickable, shows the sort caret on hover — but nothing happens unless the consumer ALSO sets `[clientSort]="true"` on the table. mm-broker shipped several detail tables with silently dead sort headers and only caught it in a browser walkthrough; nothing in types or dev mode flags the combination. The default is defensible for server-sorted lists, but the failure is invisible. **Minimum fix:** a dev-mode warning when any column has `sortable: true` while `clientSort` is false and no `(sortChange)` is bound. **Better:** make `sortable: true` mean "sort it" and let server-driven tables opt out via `[clientSort]="false"` + `(sortChange)`, which is the combination that actually knows it wants server sorting.
- [ ] **[P2] No password-requirement checklist, so every consumer writes the same one (2026-08-03, Stas — mm-broker MBP-31 review).** A "new password" field almost always sits above a live list of rules — 8 characters, an uppercase letter, a lowercase letter, a digit — each row a glyph that flips `minus → check` as the rule is met, and `minus → x` once the user has actually tried to submit. mm-broker had written that list **twice** (set-password and registration) and the two copies had already drifted: different labels for the same rule ("Contains a number" vs "One number"), a different order, and different state class names. It is one local component there now, but the work is DS-shaped: the tri-state glyph, the met/unmet colours and the type scale are all DS tokens, and nothing in it is product-specific. **Ask:** `ds-password-rules` (or a `rules` slot on `ds-input` when `type="password"`) taking the rule set plus a "judge now" flag, in one- and two-column layouts — the checklist appears both under a narrow field and beside a wide form. The consumer keeps owning the *policy*, which must mirror its own server; the DS owns the rendering. Pairs with the `error`-slot item below: a weak password is exactly the case where the helper text must not be replaced by the error.

- [ ] **[P2] A field takes one `hint` for both the helper text and the error, so every consumer multiplexes the string itself (2026-08-03, Stas — mm-broker MBP-133 review).** `ds-input` (and the rest of the field family) exposes `hint` + `invalid` + `success` but **no `error`**, so the message slot is a single input the consumer has to switch: `[invalid]="showError()"` alongside `[hint]="showError() ? errorText() : helperText()"`. Two consequences. (a) Every field grows a `computed` whose only job is picking which of two strings to pass — mm-broker has these on ten screens, and the two inputs can silently disagree (`invalid` true with the helper text still showing). (b) The helper text is *lost* while an error shows, even though it is often the thing that would fix the error ("at least 8 characters"). Material's answer is two slots — `mat-hint` and `mat-error` — with the field choosing from control state, so the consumer supplies both once and never multiplexes. Angular's own Signal Forms went the same way: the message lives with the validator and the field renders `errors()`. **Ask:** add an `error` input (or an `[error]` slot) beside `hint`, let the field prefer the error when `invalid` is set, and drop the need for `invalid` to be kept in sync by hand — deriving it from `error` being non-empty would be enough. Additive: an existing `[hint]`-only consumer is unaffected.

- [ ] **[P3] `ds-table` hands over the three layout models but never persists them, and `exportCsv()` has no affordance (2026-08-03, Stas — mm-broker MBP-133 review).** After 0.6.3/0.7.0 the table owns every feature mm-broker forked it for — `columnFilters`, `columnOrder`, `columnWidths`, `hiddenKeys`, `reorderableColumns`, `resizableColumns`, `density`, `maxHeight`, `stickyScrollbar`, `rowActions`, `total`, `sortingOrder`. Comparing surfaces, exactly **two** things keep a consumer wrapper alive: (a) **persistence** — the three column models are two-way but nothing stores them, so every consumer writes the same `localStorage` effect keyed by a screen id; (b) **the export affordance** — `exportCsv()` is a public method with no button, and a server-paged list needs to export the *whole* set, not the page, so the consumer also supplies a fetch hook. **Ask:** an opt-in `persistLayout` + `storageKey` pair that round-trips the three models, and an opt-in toolbar export button with an optional `exportFetcher` for the server-paged case. Both are small, and together they let a consumer drop its wrapper entirely instead of maintaining a subclass — see the neighbouring `sortValue` item (P1) for the third and last piece.

- [ ] **[P2] One entry point for 73 components means a consumer cannot keep the DS out of their initial bundle (2026-08-03, Stas — mm-broker MBP-133 review).** `ng-package.json` declares a single `entryFile`, so the package ships as one 1.25 MB `fesm2022` module behind a single `"."` export. `sideEffects: false` is set and tree-shaking works fine — unused components are dropped — but **chunking cannot happen**: esbuild splits by module, so it can never place two DS symbols in two different chunks. Measured in mm-broker: the app's eager composition root binds `NotificationService` to a toast implementation, that one runtime import of `ToastService` pins the whole retained DS graph into a chunk statically imported by `main`, and the result is **632 kB — about 88% of a 720 kB initial bundle** — even though every feature route is lazy and the only eagerly-needed symbol is one service. The consumer has no lever: the root is the only specifier, and moving the provider to a lazy route does not help because interceptors and the `ErrorHandler` resolve from the root injector. **Ask:** secondary entry points (ng-packagr supports a nested `ng-package.json` per folder). Even a coarse split would fix it — a services/overlay entry point carrying `ToastService`, `ModalService` and `BodyScrollLockService` separately from the component layer, so an eager root can import the service and leave 70-odd components lazy. Per-component entry points would be ideal but are a bigger change; the services split is the one that unblocks consumers. **Explicit non-goal:** nothing about the public API surface needs to change — same symbols, same names, just reachable through narrower specifiers. **RE-AUDITED 2026-08-03 → read `packaging-chunking-audit.md` before actioning this item; three claims above are wrong.** The mechanism is confirmed by controlled esbuild fixtures, but: this was never filed upstream (it is the consumer's own backlog item, with a consumer-side fix); "the consumer has no lever" is false (a dynamic `import()` keeps `main` clean — it just costs tree-shaking, measured +50%); and the 07-27 "tree-shaking already works" verdict is NOT overturned — placement and tree-shaking are orthogonal and both findings stand. The audit also merges this item with the "Packaging — secondary entry points" section below, which duplicates it with the opposite verdict.

- [ ] **[P3] A caption projected into `ds-checkbox` is silently dropped (2026-08-03, Stas — mm-broker MBP-133 review).** `checkbox.component.html` renders the caption only through the input — `@if (label()) { … {{ label() }} }` (lines 21/26) — and the component has no `<ng-content>` anywhere. So `<ds-checkbox>Accept the Terms of Service</ds-checkbox>`, which is the idiom every other body-bearing DS component accepts and the first thing a consumer tries, renders a checkbox with **no caption at all**: no error, no dev warning, nothing in the types. - [ ] **[P3] `cellTemplateMap`'s doc comment names a consumer component that is being retired (2026-08-03, Stas — mm-broker MBP-133 review; RESOLVED-HOW, just do it).** `table.component.ts:203` reads "Lets a wrapper component (e.g. **ids-data-table**) collect the directives itself and pass them down" — `ids-data-table` is mm-broker's own fork, which that review is retiring in favour of plain `ds-table`, so the library's public API doc will point at a component that no longer exists. **Correction to the original report:** it named `cellTemplateMap` *and* `emptyTemplate`; only `cellTemplateMap` carries the name. `emptyTemplate` (`:210-212`) already says "for wrappers that can't rely on slot re-projection" and needs no edit. **Do:** drop the parenthetical, leaving "Lets a wrapper component collect the directives itself…". - [ ] **[P2] Reserving the message row is right, but nothing stops a consumer stacking a form gap on top of it (2026-07-31, Stas — ai-sdlc-prototype forms migration).** `reserveMessage` defaulting to `true` is the correct call and matches Angular Material's `subscriptSizing: 'fixed'` default — the field no longer grows when an error appears, which is the whole point. What a consumer still has to discover for itself is that the reserved row lands ~23px under the control (`--field-label-gap` plus one `--font-size-xs`/`--line-height-base` line), so a form that puts its fields directly in a normal 16px stack now renders a ~39px hole between them: it reads as a layout bug, not as reserved space. ai-sdlc-prototype hit this on both of its forms the moment 0.7.0 landed, fixed it consumer-side by moving the fields into a tighter `var(--space-1)` sub-stack, and had to write the rule down (`docs/guidelines/forms.md`) so the next form would not repeat it — every consumer will rediscover the same thing. Material avoids the trap by owning the field's vertical rhythm inside `mat-form-field` instead of leaving the inter-field gap to the host.

  **RESOLVED 2026-08-03 — docs-only, build nothing.** The premise that the DS lacks the primitive is wrong: `ds-stack` already ships with `gap="none|xs|sm|md|lg|xl"` (`stack.component.scss`), and `gap="none"` is *exactly* the right value for a column of message-bearing fields — with `reserveMessage` on, the field's own box already ends in the rhythm (`--field-label-gap` 6px + one `--font-size-xs` 12px × `--line-height-base` 1.4 line = 22.8px), so any stack gap on top of it is double-counting. ai-sdlc's consumer-side fix (`var(--space-1)` sub-stack) is `gap="xs"` — close, and it worked, but it treats a correct default as something to compensate for. **So:** no `ds-field-stack`, no `--ds-field-stack-gap` (`--ds-stack-gap` already covers the escape hatch), no dev warning. **Do instead:** a block in ds-docs `patterns/form-layout` pairing `reserveMessage` with the stack gap it expects, with a live side-by-side of the failure (`gap="md"` → the ~39px hole) and the fix (`gap="none"`), plus one line on the wrinkle that motivates the confusion — **a MIXED stack is the genuinely awkward case**: put a `reserveMessage="false"` field, a button row or a non-message control in the same `gap="none"` column and the rhythm goes ragged, because only some children carry their own trailing space. Name that case explicitly and tell the consumer to give it its own stack.

  **SUPERSEDED 2026-08-04 — Stas reversed the default instead.** `reserveMessage` now defaults to **`false`** and is opted into where a form validates (see `CHANGELOG.md` → Unreleased → Changed, and `migrations/unreleased.json` → `field-reserve-message-default-off`). That removes the ~39px hole at the source: a plain 16px stack is correct again for the common hint-less form, and `gap="none"` becomes the pairing for the *opted-in* case rather than the default one. **What survives of this item:** the docs work, reframed — `patterns/form-layout` and the `ds-input` section were updated with the flip, but the live side-by-side demo (`gap="md"` hole vs `gap="none"`) and the MIXED-stack wrinkle were NOT built and are still worth doing. **Group opt-in shipped 2026-08-04:** `dsReserveMessages` on a form turns the row on for every field declared inside it, and a nested `provideDsConfig` now merges rather than shadows — the latter was a latent footgun this question surfaced (scoping one field flag silently reset `datePicker.locale` / `timePicker.format` / `breadcrumbs.separator`). **Also note:** this item and my 08-03 resolution both stated "do not change the `reserveMessage` default" as an explicit non-goal, on the [[feedback-opt-in-features]] reading that flipping an existing default is forbidden. Stas's call is that the rule's intent — capabilities off until asked for — argues FOR the flip, since reserving space is the capability. Recorded so the reversal reads as a decision, not a drift. `ds-stack`'s default gap is still not to be changed.

## Packaging — secondary entry points (optional, future)

> **PARTLY SUPERSEDED 2026-08-03 — see `packaging-chunking-audit.md`.** The tree-shaking verdict below still holds, but this section's revisit-trigger list is what failed: it never anticipated "one eager service import drags the whole component layer into the initial chunk", which is the case that actually arrived. This section and the P2 item under "Component feature gaps" are two records of one question — merge them.
>
> **Not needed for correctness — tree-shaking already works.** Verified 2026-07-27 via a linker+esbuild pseudo-build on `dist/ds`: bundle size scales with imports (Button-only < 6-component subset < whole lib), so unused components ARE dropped by a consumer's production build. Precondition holds: root `package.json` `"sideEffects": false` + 81 standalone components + ESM FESM. Consider secondary entry points ONLY if the lib grows much larger or we want guaranteed per-component chunks / lazy loading.

**What it is.** Ship the library as many small sub-packages under one name, à la `@angular/material/button`, `@angular/cdk/overlay`. Consumers import `@ids-group-ltd/ids-design-system/button` instead of the single barrel. Each entry point is its own module graph the bundler reasons about independently.

**Why (beyond what we already have).**
- Bundler-agnostic tree-shaking: even a naive/older bundler, or a consumer doing `import * as DS`, gets only the entry point it touched — no reliance on `sideEffects` + DCE being perfect.
- True lazy loading: `import('@ids-group-ltd/ids-design-system/date-picker')` splits date-picker into its own async chunk.
- Faster consumer rebuilds, clearer dependency edges.

**Current state (single entry point).** `ng-package.json` → `lib.entryFile: src/public-api.ts`; one barrel re-exports all ~74 component folders → one FESM (`dist/ds/fesm2022/…mjs`, ~1.2 MB raw). Styles ship separately as raw SCSS assets under `styles/` + `themes/` — unaffected by this change.

**What to do (ng-packagr secondary entry points).**
1. In each component folder that becomes its own entry point, add a minimal `ng-package.json` + a local `public-api.ts`. Example — `src/lib/components/button/`:
   - `ng-package.json`: `{ "lib": { "entryFile": "public-api.ts" } }`
   - `public-api.ts`: `export * from './button.component'; export type * from './button.types';`
   ng-packagr auto-discovers nested `ng-package.json` under the primary source root and emits a secondary entry point named by folder path (→ `@ids-group-ltd/ids-design-system/button`).
2. Keep the root `public-api.ts` as a **facade** re-exporting the secondary entry points, so the current barrel import keeps working — no forced breaking change; new code opts into the granular path.
3. Secondary entry points may **not** deep-import each other's internals (`../modal/modal.component`) — they must go through the sibling's public entry, or share via a `core`/`internal` entry point. ng-packagr errors on cross-entry deep imports, which is exactly what surfaces hidden coupling.
4. Shared internals (icons, overlay/portal helpers, `core/status`, config, theme) → their own entry points (`…/icons`, `…/core`) that components depend on.

**How it looks in our case.**
```ts
// today (kept working as a facade):
import { ButtonComponent, DatePickerComponent } from '@ids-group-ltd/ids-design-system';
// after (granular, opt-in):
import { ButtonComponent } from '@ids-group-ltd/ids-design-system/button';
import { DatePickerComponent } from '@ids-group-ltd/ids-design-system/date-picker';
// lazy:
const { DatePickerComponent } = await import('@ids-group-ltd/ids-design-system/date-picker');
```

**Cost / caveats.** ~74 tiny `ng-package.json` + `public-api.ts` pairs to add + maintain (scriptable via a generator); cross-entry imports must launder through public entries — a one-time refactor that also **exposes and forces fixing real coupling**; slightly longer lib build; styles/tokens layer unchanged (already asset-based).

**Verdict:** defer. Revisit if (a) component count roughly doubles, (b) a consumer needs route-level lazy loading of a heavy component (date-picker/table/color-picker/tree), (c) we want tree-shaking guaranteed independent of consumer bundler quality, or (d) **an eager consumer graph needs ONE service and thereby pins the whole component layer into the initial chunk** — trigger (d) fired on 2026-08-03 in mm-broker (`ToastService` via `provideCommon`); the decision itself is still open, see `packaging-chunking-audit.md` §7.
