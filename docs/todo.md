- [ ] **Button API: split `variant` into `color` × `fill` (model corrected 2026-06-11).** User's intent: `primary/secondary/tertiary` are **COLOR ROLES** (brand hues — the theme already holds full channel-recomposing families `--secondary-*`/`--tertiary-*`, defaulting to primary; a brand sets e.g. orange secondary), NOT hierarchy levels. So two axes: `color: primary | secondary | tertiary | neutral | error | success | warning` (which hue family) × `fill: solid | tonal | ghost | outline` (fill pattern). Defaults `color="primary" fill="solid"`. Old→new mapping: `primary`→primary/solid · `secondary`→**primary**/tonal (old "secondary" was never the secondary color) · `tertiary`→primary/ghost · `outline`→neutral/outline · `error|success|warning`→status/solid · **`text`→DROPPED, use global `.link` class on `<button>`** (loses loading/fullWidth — acceptable). Hard rename, NO aliases (we are the only consumers; migrate lib + ds-docs in one pass). Implementation: color classes remap `--c-*` family slots, fill classes consume them — no per-color duplication; public `--ds-button-*` layer unchanged on top. Theme gaps found: no `*-muted-strong` step for secondary/tertiary/statuses (tonal hover; prototype uses `hsl(h,90%,89%)` formula / `*-border`) — add roles; focus rings exist only neutral+error; secondary/tertiary families are formula-derived — hand-tune ramp picks when their buttons are legalized (see memory). Superseded earlier Polaris `variant+tone` sketch (2026-06-10, commit `3563b4d`). Live prototype with brand-recolor knobs + per-combo verdict stamps: `presentations/button-variant-tone.html`. Spec must also cover (analysis 2026-06-11): (a) **button was the lib's outlier** — badge/tabs/status-dot/stat/sidenav/page-header already use `secondary` as the COLOR role, so this fixes an internal inconsistency; (b) **icon-button rides the same pass** — its `standard/filled/tonal/outline` variants are already fills (primary-family pinned), add the same `color` input; (c) **combos are NOT compile-time enforceable** across two Angular inputs — use dev-mode `console.warn` on banned pairs + docs (correcting the prototype's "compiler will narrow" claim); (d) **solid contrast risk**: `--secondary/tertiary-on` default to white — light brand hues fail AA; brand must override `-on` (same mechanic as the existing "Primary-button CTA token layer" todo — consider solving together); (e) migration is small: 87 `variant=` usages in lib+ds-docs (outline 32, error 13, secondary 11, primary 10, success 8, text 7, warning 6) + `_forced-states` mirrors; (f) `.link` may need color modifiers (`.link.error`) to fully replace `variant="text"` × status. - [ ] **`ds-color` attribute — scoped accent recolor (proposed 2026-06-11, grew out of the button color×fill work; naming settled with user: attribute `ds-color="…"`, NOT a `.ds-accent-*` class — one word with the button's `color` input).** Survey: 36 component stylesheets paint their accent from the primary family (checkbox/radio/switch checked fill, pagination active, tabs indicator, date-picker selected day, stepper, dropzone, spinner, progress, tag solid, avatar fallback, field focus borders…); only 6 support secondary (each via its own hand-rolled remap — tabs `.secondary` class, sidenav rail); `--tertiary` is used by NOBODY. Instead of adding a `color` input to ~30 components: ONE rule body remapping the primary family (`--primary→--secondary`, `-hover/-strong/-subtle/-muted/-muted-strong/-on` + channels), FOUR application levels: (1) app config for ALL instances of a type — SCSS mixin `ds.color()` in consumer styles (`ds-switch { @include ds.color(secondary) }`); (2) zone — `<div ds-color="secondary">` recolors the subtree; (3) single instance — same attribute on the component host (`<ds-switch ds-color="secondary">`, custom props inherit host→template), which is WHY no per-component input is needed; (4) typed `color` input — button/icon-button only (color participates in logic there: banned fill combos, status ramps, dev-warnings). Attribute survives potential component→CSS-class demotions (audit track) and covers future components for free. Gotchas for the spec: (1) ramp-pick tokens (`--primary-muted: var(--blue-100)`) don't recompose from channels — remap each token by name; (2) `:root`-composed tokens (`--focus-ring` builds from primary channels at :root) resolve at declaration point — must be re-declared inside the scope; (3) needs the same `*-muted-strong` role gap fixed. Open: status values (`ds-color="error"` for form danger zones)? **Semantics review (2026-06-12): prefer an `--accent-*` indirection layer over remapping `--primary` in place** — remap-in-place makes the role LIE inside the scope and `ds-color="primary"` (reset inside a colored zone) impossible (originals overwritten by cascade); instead components read `--accent-*` (`:root` defaults it to the primary family), `ds-color` remaps only `--accent-*`, roles never lie, reset is trivial (Radix Themes model). Cost: one sweep over the 36 components switching accent reads `--primary*`→`--accent*`. User confirmed the pointer principle 2026-06-12 ("не переписывать primary, а значение, от которого пляшет применение") — same mechanism at both levels: button's `--c-*` slots = component-local pointer flipped by the input's host class; `--accent-*` = theme-global pointer flipped by the `ds-color` cascade. Unification: default the button's `--c-*` slots to `var(--accent-*)` (not `var(--primary*)`) so buttons WITHOUT an explicit `color` input follow the zone too; an explicit instance `color` still wins (component class is declared closer than the inherited zone value). Also decide: bare `ds-color` attribute is not valid HTML5 (custom attrs = `data-*`); Angular ecosystem precedent says fine (Material attr selectors) — settle in spec. Precedents validating the whole model: M3 (filled/tonal/outlined/text × primary/secondary/tertiary roles = literally our axes), Radix nested `<Theme accentColor>` (zone), Vuetify defaults / MUI defaultProps / Ant ConfigProvider (per-type config). Cleanup: retire tabs' hand-rolled `.secondary` remap as a special case. All four levels live-demoed in `presentations/button-variant-tone.html`. Depends on / pairs with the Button color×fill item above.
- [ ] **Single-source colour engine — collapse `--primary` + `--primary-h/s/l` into ONE token, derive the rest with `color-mix()` + relative-colour (idea 2026-06-24, Stas).** ROOT CAUSE this fixes (surfaced when a consumer wrote `[data-theme='dark'] ds-checkbox { --primary-h/s/l: … }` to recolour a checkbox and ONLY the focus halo changed): "primary" today has TWO decoupled representations — **(a)** `--primary` + role shades (`-hover/-pressed/-strong/-subtle/-muted/-muted-strong`) are **hand-picked ramp values** (`--blue-600/700/100/50…`), read by component FILLS (`checkbox.component.scss` checked fill/border = `var(--primary)`); **(b)** `--primary-h/s/l` are **HSL channels** that feed ONLY math-derived bits — translucent halos (`--focus-field` `:256`, `--focus-ring` outer `:243`), the `--blue-*` ramp generation (`--blue-600: hsl(var(--blue-h) var(--blue-s) var(--blue-l))`), gray tinting (`--neutral-h: var(--primary-h)`), `--link-visited`. They only mirror by default (`--primary-h: var(--blue-h)`, `--primary: var(--blue-600)`) with **no live link**: overriding `--primary-h/s/l` does NOT move `--primary` (fill keeps old hue — `--primary`→`--blue-600`→`--blue-h`, not `--primary-h`), and overriding `--primary` does NOT move the channel-derived halos/ramp. So a coherent scoped recolour needs BOTH the channels AND a `--primary` re-composition — the awkward 3-/4-token override, and a footgun (half silently no-ops; the checkbox snippet above retints only the ring, not the fill).
  **IDEA:** make ONE colour token per role (`--primary`, `--error`, `--neutral` base) the only source and derive everything from it with modern CSS — relative-colour is Baseline (Chrome 119 / Safari 16.4 / Firefox 128, since 2023–24), `color-mix()` earlier, both safe for the lib's evergreen target:
  - shades / states via `color-mix()` (DS ALREADY does this for hover/pressed: `color-mix(in srgb, var(--primary) 88%, black)`) — extend to halos: `--focus-field: 0 0 0 3px color-mix(in srgb, var(--primary) 22%, transparent)` replaces `hsl(h s l / .22)`;
  - hue extraction via relative-colour: `hsl(from var(--primary) h <s> <l>)` / `oklch(from var(--primary) <l> c h)` — pulls the hue from the one token while each step keeps its **hand-tuned S/L** (e.g. `--primary-strong: hsl(from var(--primary) h 85% 42%)`), so the designed ramp is preserved, NOT formula-flattened (see memory [[feedback-handtuned-colors-beat-formulas]] — only the HUE is single-sourced; per-step S/L stay hand-picked);
  - drop `--primary-h/s/l` as PUBLIC API (keep at most internal `from`-derived); `--neutral-h`/ramp source their hue from the one token too.
  Roles stay overridable (consumer-first / read-with-fallback, like the `--ds-*` component layer): each `--primary-*` is still a named token DEFAULTING to the derivation, so a brand can pin any single step by hand. **PAYOFF:** scoped recolour becomes ONE declaration — `ds-checkbox { --primary: hsl(5 92% 64%) }` and fill + border + hover + halo all follow — which is exactly what **UNBLOCKS the `ds-color` / `--accent-*` indirection item above**: kills its gotcha (1) "ramp-pick tokens don't recompose from channels" and (2) "`:root`-composed tokens resolve at declaration point" — with single-source + color-mix/relative there are no channels to re-declare and no compose-point trap; `--accent` becomes a single pointer the zone/attr flips and all shades cascade.
  **OPEN for the spec:** (a) colour space for the math — `oklab`/`oklch` (perceptually-uniform mix-to-black/lighten, but shifts the current look) vs `srgb`/`hsl` (matches today's `color-mix`); verify each derived role visually before switching; (b) which roles are pure-derived vs keep an explicit hand-pick (ramp steps likely stay hand-picked-with-sourced-hue; hover/pressed/halo are the clean formula candidates); (c) relative-colour + `var()` substitution edge cases — verify in the 3 target engines; (d) interplay with the forced-colors/HC theme + future dark theme (the `--focus-field-alpha` token already anticipates a dark-boost). Pairs with the "Theme recipe vs hand-tuned picks" decision and "Палитра — остаточная чистка". Live interactive demo (one `--primary` knob → all shades/halo/checkbox follow via `color-mix` + `hsl(from …)`; today-vs-proposed side-by-side): **`presentations/color-engine-relative.html`**.

- [ ] **Global `focus type` config — switch the focus-indicator style theme-wide (idea 2026-06-18).** Today there are two fixed focus families: `--focus-field` (soft 3px halo — fields: input/textarea/select/search/dropdown/number-stepper/combobox) and `--focus-ring` (crisp 2px ring + canvas gap — actions/nav/inline: button/checkbox/radio/switch/tabs/link/…). Idea: let a brand/app pick the focus *look* in one place (theme token or `[data-focus="…"]` on `:root`) across the whole DS, choosing between **4 styles**: (1) **focus-field** (current soft halo); (2) **focus-ring** (current crisp ring); (3) **B — offset-outline** (`outline: 2px solid primary; outline-offset: 2px` — no box-shadow; survives Windows High-Contrast / forced-colors, where box-shadow rings vanish); (4) **C — contiguous primary edge** (border→primary + flush 1px primary ring = one 2px primary kant, no gap/halo). - [ ] **open listbox doesn't close on Tab** (combobox/select/dropdown) — overlay stays up and focus escapes behind it; Escape is handled, Tab isn't. **(P1)**

### From PIN-475 Kit Movement filters prototype (Stas, 2026-06-17)
Gaps hit while building filter toolbars with `ds-combobox` / `ds-select` / `ds-search`:
- [ ] **combobox: no content/compact width** — a multi-select `ds-combobox` always fills its host width, so a single short chip leaves a wide empty trigger to its right (looks broken in a toolbar). Want an intrinsic/`fit-content`-ish sizing mode, or at least a `max-content` cap, so the trigger hugs its chips + a min typing area. (Today the consumer has to hard-cap the host width as a workaround.)
- [ ] **combobox single-select still reads as a free-text input** — in single mode the trigger keeps the typeable search-input affordance + chevron even after a value is picked, so a "pick exactly one" control looks identical to a multi/typeahead and to `ds-select`. Consider a single-select display mode that reads as a filled select (selected label, no lingering empty input), or guidance on when to use `ds-select` vs `ds-combobox`.
- [~] **focus ring reads as a double outline on inputs** — **root cause found 2026-06-18 (was misdiagnosed).** The screenshot's double ring (outer pink + white gap + inner teal) was NOT the DS control's own border+shadow. It was an APP-side leak: pinkmoon's global `_forms.scss` `.input:focus { box-shadow: 0 0 0 3px rgba(0,172,170,.35) /* topaz */ }` matched the native `<input class="input">` *inside* `ds-search` (Angular emulated encapsulation doesn't shield a component's inner element from a global class selector), stacking a teal ring INSIDE ds-search's own pink `:focus-within` ring; the white container bg between them = the "gap". **Fixed in pinkmoon** (`prototype/projects/admin/src/styles/_forms.scss`, 2026-06-18): `:is(ds-search,ds-combobox,ds-select,ds-input) .input:focus { box-shadow: none; border-color: inherit; }` — keeps the global field styles out of DS internals (admin build green). User scoped the fix to pinkmoon only; DS lib left untouched. **DS-side follow-ups still open (real, separate from the leak):** (1) `ds-search` names its inner input with the over-generic `.input` class — a leaky surface any consumer `.input` reset bleeds into (combobox already scopes via `.combo-input`); consider renaming to a scoped class so the lib is immune. (2) ✅ **Token inconsistency FIXED 2026-06-18.** `ds-combobox` focus was on `--focus-ring` (2px `--surface-canvas` gap + solid primary = a genuine double-band, ugly on dark bg) while `ds-select`/`ds-search`/`ds-input`/`ds-dropdown`/`ds-number-stepper` use the softer `--focus-field`. Changed `combobox.component.scss` `:focus-within` `box-shadow: var(--focus-ring)` → `var(--focus-field)` (one line; lib build green, stylelint clean). The FIELD family is now 100% uniform on `--focus-field`; `--focus-ring` stays for actions/nav/inline (button/checkbox/radio/switch/tabs/link/menu/card/pagination/sidenav/date-picker/toast) — the deliberate two-tier system (fields → field-halo, actions → crisp ring), NOT an inconsistency. A theme-wide `focus type` switch (field/ring/B/C) is logged under Missing tokens / foundations. Live A/B/C comparison (incl. dark-bg strip + baseline-impl breakdown) → `presentations/pin-475-fields.html`.
- [ ] **"Glued field" / adornment composer — one bordered control from a leading select + trailing input (proposed 2026-06-18, Stas).** PIN-475's search bar needs a single field that reads as `[ "search by" select ▾ | divider | text input OR product autocomplete ]` — one shared border + one focus ring, fixed-width left segment, flexible right segment. `ds-select` can't be a leading addon: it has no fit-content width (it fills the host — already logged above) and no API to drop its own border/radius so it blends into a shared chrome. Precedents: Chakra `InputGroup`/`InputLeftAddon`, MUI `OutlinedInput` adornments, Ant `Input.Group`/`Space.Compact`, Bootstrap input-group. Pairs with the combobox fit-content + single-select-display items above (those are the leading-segment's blockers). Live local impl to mine for the spec: `prototype/projects/admin/src/app/shared/search-scope/search-scope.component.ts`.
