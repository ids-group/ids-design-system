- [ ] **`ds-color` attribute — scoped accent recolor (proposed 2026-06-11, grew out of the button color×fill work; naming settled with user: attribute `ds-color="…"`, NOT a `.ds-accent-*` class — one word with the button's `color` input).** Survey: 36 component stylesheets paint their accent from the primary family (checkbox/radio/switch checked fill, pagination active, tabs indicator, date-picker selected day, stepper, dropzone, spinner, progress, tag solid, avatar fallback, field focus borders…); only 6 support secondary (each via its own hand-rolled remap — tabs `.secondary` class, sidenav rail); `--tertiary` is used by NOBODY. Instead of adding a `color` input to ~30 components: ONE rule body remapping the primary family (`--primary→--secondary`, `-hover/-strong/-subtle/-muted/-muted-strong/-on` + channels), FOUR application levels: (1) app config for ALL instances of a type — SCSS mixin `ds.color()` in consumer styles (`ds-switch { @include ds.color(secondary) }`); (2) zone — `<div ds-color="secondary">` recolors the subtree; (3) single instance — same attribute on the component host (`<ds-switch ds-color="secondary">`, custom props inherit host→template), which is WHY no per-component input is needed; (4) typed `color` input — button/icon-button only (color participates in logic there: banned fill combos, status ramps, dev-warnings). Attribute survives potential component→CSS-class demotions (audit track) and covers future components for free. Gotchas for the spec: (1) ramp-pick tokens (`--primary-muted: var(--blue-100)`) don't recompose from channels — remap each token by name; (2) `:root`-composed tokens (`--focus-ring` builds from primary channels at :root) resolve at declaration point — must be re-declared inside the scope; (3) needs the same `*-muted-strong` role gap fixed. Open: status values (`ds-color="error"` for form danger zones)? **Semantics review (2026-06-12): prefer an `--accent-*` indirection layer over remapping `--primary` in place** — remap-in-place makes the role LIE inside the scope and `ds-color="primary"` (reset inside a colored zone) impossible (originals overwritten by cascade); instead components read `--accent-*` (`:root` defaults it to the primary family), `ds-color` remaps only `--accent-*`, roles never lie, reset is trivial (Radix Themes model). Cost: one sweep over the 36 components switching accent reads `--primary*`→`--accent*`. User confirmed the pointer principle 2026-06-12 ("не переписывать primary, а значение, от которого пляшет применение") — same mechanism at both levels: button's `--c-*` slots = component-local pointer flipped by the input's host class; `--accent-*` = theme-global pointer flipped by the `ds-color` cascade. Unification: default the button's `--c-*` slots to `var(--accent-*)` (not `var(--primary*)`) so buttons WITHOUT an explicit `color` input follow the zone too; an explicit instance `color` still wins (component class is declared closer than the inherited zone value). Also decide: bare `ds-color` attribute is not valid HTML5 (custom attrs = `data-*`); Angular ecosystem precedent says fine (Material attr selectors) — settle in spec. Precedents validating the whole model: M3 (filled/tonal/outlined/text × primary/secondary/tertiary roles = literally our axes), Radix nested `<Theme accentColor>` (zone), Vuetify defaults / MUI defaultProps / Ant ConfigProvider (per-type config). Cleanup: retire tabs' hand-rolled `.secondary` remap as a special case. All four levels live-demoed in `presentations/button-variant-tone.html`. Depends on / pairs with the Button color×fill item above.

This is the blocker and pairs with the "clickable steps + error state + vertical" gaps already under Component feature gaps → Display — the **vertical** variant in particular is near-useless without visible labels (labels sit to the right of each node). Stepper also has NO public token API (already logged under "Components with NO public tokens at all") — visible labels will need label typography/color/active-weight tokens.
