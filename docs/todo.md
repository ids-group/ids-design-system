## Architecture / tokens

- [ ] **Single-source colour engine — collapse `--primary` + `--primary-h/s/l` into ONE token, derive the rest with `color-mix()` + relative-colour (idea 2026-06-24, Stas).** ROOT CAUSE this fixes (surfaced when a consumer wrote `[data-theme='dark'] ds-checkbox { --primary-h/s/l: … }` to recolour a checkbox and ONLY the focus halo changed): "primary" today has TWO decoupled representations — **(a)** `--primary` + role shades (`-hover/-pressed/-strong/-subtle/-muted/-muted-strong`) are **hand-picked ramp values** (`--blue-600/700/100/50…`), read by component FILLS (`checkbox.component.scss` checked fill/border = `var(--primary)`); **(b)** `--primary-h/s/l` are **HSL channels** that feed ONLY math-derived bits — translucent halos (`--focus-field` `:256`, `--focus-ring` outer `:243`), the `--blue-*` ramp generation (`--blue-600: hsl(var(--blue-h) var(--blue-s) var(--blue-l))`), gray tinting (`--neutral-h: var(--primary-h)`), `--link-visited`. They only mirror by default (`--primary-h: var(--blue-h)`, `--primary: var(--blue-600)`) with **no live link**: overriding `--primary-h/s/l` does NOT move `--primary` (fill keeps old hue — `--primary`→`--blue-600`→`--blue-h`, not `--primary-h`), and overriding `--primary` does NOT move the channel-derived halos/ramp. So a coherent scoped recolour needs BOTH the channels AND a `--primary` re-composition — the awkward 3-/4-token override, and a footgun (half silently no-ops; the checkbox snippet above retints only the ring, not the fill).
      **IDEA:** make ONE colour token per role (`--primary`, `--error`, `--neutral` base) the only source and derive everything from it with modern CSS — relative-colour is Baseline (Chrome 119 / Safari 16.4 / Firefox 128, since 2023–24), `color-mix()` earlier, both safe for the lib's evergreen target:
  - shades / states via `color-mix()` (DS ALREADY does this for hover/pressed: `color-mix(in srgb, var(--primary) 88%, black)`) — extend to halos: `--focus-field: 0 0 0 3px color-mix(in srgb, var(--primary) 22%, transparent)` replaces `hsl(h s l / .22)`;
  - hue extraction via relative-colour: `hsl(from var(--primary) h <s> <l>)` / `oklch(from var(--primary) <l> c h)` — pulls the hue from the one token while each step keeps its **hand-tuned S/L** (e.g. `--primary-strong: hsl(from var(--primary) h 85% 42%)`), so the designed ramp is preserved, NOT formula-flattened (see memory [[feedback-handtuned-colors-beat-formulas]] — only the HUE is single-sourced; per-step S/L stay hand-picked);
  - drop `--primary-h/s/l` as PUBLIC API (keep at most internal `from`-derived); `--neutral-h`/ramp source their hue from the one token too.
    Roles stay overridable (consumer-first / read-with-fallback, like the `--ds-*` component layer): each `--primary-*` is still a named token DEFAULTING to the derivation, so a brand can pin any single step by hand. **PAYOFF:** scoped recolour becomes ONE declaration — `ds-checkbox { --primary: hsl(5 92% 64%) }` and fill + border + hover + halo all follow — which is exactly what **UNBLOCKS the `ds-color` / `--accent-*` indirection item above**: kills its gotcha (1) "ramp-pick tokens don't recompose from channels" and (2) "`:root`-composed tokens resolve at declaration point" — with single-source + color-mix/relative there are no channels to re-declare and no compose-point trap; `--accent` becomes a single pointer the zone/attr flips and all shades cascade.
    **OPEN for the spec:** (a) colour space for the math — `oklab`/`oklch` (perceptually-uniform mix-to-black/lighten, but shifts the current look) vs `srgb`/`hsl` (matches today's `color-mix`); verify each derived role visually before switching; (b) which roles are pure-derived vs keep an explicit hand-pick (ramp steps likely stay hand-picked-with-sourced-hue; hover/pressed/halo are the clean formula candidates); (c) relative-colour + `var()` substitution edge cases — verify in the 3 target engines; (d) interplay with the forced-colors/HC theme + future dark theme (the `--focus-field-alpha` token already anticipates a dark-boost). Pairs with the "Theme recipe vs hand-tuned picks" decision and "Палитра — остаточная чистка". Live interactive demo (one `--primary` knob → all shades/halo/checkbox follow via `color-mix` + `hsl(from …)`; today-vs-proposed side-by-side): **`presentations/color-engine-relative.html`**.

### Motion system audit — abrupt state changes (2026-06-26, 4 parallel agents vs code)

Goal: a coherent, **smooth** motion system. **Foundation is healthy** — motion tokens (`--duration-instant/fast/base/slow/slower`, `--duration-loop-fast/slow`; `--ease-standard/emphasized/decelerate/accelerate/spring`) are used CONSISTENTLY (audit found **0 hardcoded durations/easings**) and reduced-motion is zeroed globally in `_tokens.scss`. The problem is **breadth, not chaos**: many interactive state changes have NO `transition` and so SNAP. **Already smooth — leave as reference:** toast (enter + `.leaving` + `animationend` teardown), progress (determinate width + indeterminate loop), bottom-sheet (close shipped 2026-06-25), card (lift+shadow), icon-button, menu-item, breadcrumbs, tag, w3w, `.link`; avatar/divider/status-dot are static. **Reference patterns to replicate:** animate-then-remove = `bottom-sheet.component.ts` / `toast-region`; state-change transition = `input.component.scss` (border/bg/shadow on `--duration-fast --ease-standard`). Findings grouped, ~highest payoff first (file:line are agent evidence — re-confirm at fix time per [[feedback-validate-before-applying]]):

- [ ] **Rounded `:active` touch-feedback for stateful controls (follow-up to the tap-highlight reset, 2026-06-30).** The global tap-highlight reset (`_reset.scss` `html, body { -webkit-tap-highlight-color: transparent }`, commit `d4c5811`) removed the native Android overlay — which on touch was the ONLY press feedback for controls that have **no explicit `:active`**. They don't "die" (the press is still felt via the state change / panel open — checked-fill, dropdown open, navigation), but for an ideal tactile tap they should each get a **rounded** `:active`. **Requirement:** draw it as `background`/`box-shadow` on the element that carries the `border-radius` so it inherits the shape — NEVER a square overlay. **Components WITHOUT an explicit `:active`** (Stas-named: checkbox, radio, switch, list-item, menu-item, select; per the full interactive-component map also: dropdown, segmented, tabs-standard, tag host, pagination, sidenav-item, calendar-day, toggle-button, combobox, multi-select, color-picker). NOT a bug — an enhancement. **Pairs with the `.ds-interactive` global state contract** (Architecture/tokens above) — better to define the pressed step there once than per-component.
  - _Background — why the reset was global, not per-component clipping:_ the native Android tap overlay is a **rectangle drawn over the tapped element that ignores the element's own `border-radius`** (square corners poke past pill/rounded controls — client-facing bug on the mm-broker employee-portal, Stas 2026-06-30). It is clipped ONLY by a *tight* ancestor with `overflow:hidden` + `border-radius`. That is why the prototype's welcome CTA looked fine while every other control showed the square: its `.cta` host wraps the `<button>` 1:1 with `overflow:hidden`+pill, an **accidental clip** — confirmed on-device, the turquoise overlay IS present but pill-shaped. Relying on a tight clip per control is fragile, so the fix is global `transparent` + each control's own rounded `:active`.

- [ ] **modal/drawer scroll-lock isn't ref-counted** — with two overlays stacked, closing the first restores body scroll under the second (both just reset `body.style.overflow`). **(P1)** — DEFERRED 2026-07-06 (Stas: "пропусти, распиши варианты"). modal (`modal.component.ts` overflow effect) + drawer (`drawer.component.ts` overflow effect) write `body.style.overflow = ''` unconditionally on close; bottom-sheet uses save/restore (`previousBodyOverflow`) — better, but still per-instance, not shared. Stacked overlays of ANY mix (modal over drawer, bottom-sheet over modal, …) → closing the inner one unlocks body scroll while an outer one is still open. A real fix needs SHARED state (a counter); a per-component tweak can't coordinate across component types. **Options:**
  - **(A) Ref-counted lock service (recommended).** A tiny injectable singleton (e.g. `src/lib/.../scroll-lock.service.ts`): `lock()` increments a counter and on 0→1 saves `body.style.overflow` then sets `hidden`; `unlock()` decrements and on 1→0 restores the saved value. modal/drawer/bottom-sheet call `lock()`/`unlock()` from their `rendered` effect + `DestroyRef`. Correct for any nesting/order. Cost: one new shared-service pattern (needs the "no new pattern without asking" sign-off — already flagged to Stas).
  - **(B) CDK `BlockScrollStrategy`** (`overlay.scrollStrategies.block()`). Reuses CDK's own scroll-block. BUT modal/drawer/bottom-sheet do NOT use CDK overlay (they render via `@if` + `position: fixed`), so a CDK strategy has to be created + enabled/disabled artificially just for the body lock — awkward, and still needs per-instance coordination. Less natural here.
  - **(C) Per-component save/restore only** — give modal + drawer the same `previousBodyOverflow` save/restore bottom-sheet has. Cheapest, but order-dependent and does NOT robustly fix stacking across different component types (each captures/restores independently). A partial patch, not a real fix — rejected.
- [x] ~~**accordion `aria-controls` dangles when collapsed**~~ — ❌ NOT A BUG (verified-vs-code 2026-06-25). The `<div role="region" [id]="bodyId">` is rendered UNCONDITIONALLY (`accordion-item.component.html:22`), toggled only via `[class.is-open]` + `[attr.inert]` — never inside an `@if`. So `aria-controls` always resolves. No fix needed; finding was stale/incorrect.
- [ ] **date-picker grid semantics** — no `role="grid"`/`row`/`columnheader`/`gridcell` model (uses `aria-pressed`); popup has no `role="dialog"`/name. **(P2)** — DEFERRED 2026-07-06 (Stas: "отложить"). The day grid is a flat CSS `grid` of `.dow` spans + `<ds-calendar-day>` buttons; selection uses `aria-pressed` (toggle-button) instead of `aria-selected` (grid-cell). Per the APG **Date Picker Dialog** example the calendar should be a `role="grid"` (rows / `columnheader` day names / `gridcell` days) with `aria-selected` on the one selected cell, plus `role="dialog"` + accessible name on the popup (the trigger already advertises `aria-haspopup="dialog"`). **Why deferred:** the pieces are COUPLED — `aria-selected` is only valid on an element with a grid/listbox role, so switching `aria-pressed`→`aria-selected` REQUIRES first building the grid role structure (group `daysGrid()` into week rows, wrap in `role="row"` — likely `display:contents` to keep the CSS grid layout intact). Non-trivial + real layout risk for a P2. Roving-tabindex + arrow-key nav are ALREADY present (`isFocusDay` + `onGridKeydown`); the old `setTimeout`-on-disposed-overlay focus concern is already fixed (`afterNextRender` + guard — re-verified NOT a bug 2026-07-06). Source: APG Date Picker Dialog (`w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog`).
- [ ] **badge `count` `aria-label` wording is hardcoded "notifications"** (minor — surfaced 2026-07-06 while verifying the count-label finding, which is itself DONE). `badge.component.ts` `countAriaLabel()` returns `"${value} notifications"` / `"More than ${max} notifications"`, but `ds-badge [count]` is used for ANY numeric count (cart items, unread, search results), so a cart badge announces "3 notifications" — misleading and not i18n-able. The `aria-label` IS present (original finding satisfied); this is a follow-up. Fix: make the noun configurable — a `countLabel`/`unit` input or an `ariaLabel` override, defaulting to the current wording. Low priority.
- [ ] **bottom-sheet Escape is a document-level `(document:keydown.escape)`** (from `a11y-branch-review.md`, not previously on the board; re-confirmed 2026-07-06). modal/drawer scope their Escape to the panel; bottom-sheet listens at document level (`host: { '(document:keydown.escape)': 'onEscape()' }`), so with stacked overlays Escape could be consumed by the wrong sheet. Low risk (bottom-sheet is rarely stacked), align to a panel-scoped binding for consistency when next touching it. (Dialog semantics + `cdkTrapFocus` were added 2026-07-06; this scoping is the remaining polish.)
- [ ] **API consistency (P2)** — `booleanAttribute` on all boolean inputs; `danger`→`error` / `warn`→`warning`; dropdown `error`→`invalid`; `radio.name` type; export `DividerSpacing`/`PopoverAlign`; button size scale (FULL finding promoted to Architecture/tokens — dual `s/m/l`+`sm/md/lg` tiers, collapse with the color×fill rework); output-name unification; pagination model/output dedup; `title` requiredness unification (modal `required` vs drawer/bottom-sheet/banner optional). Gaps hit while building filter toolbars with `ds-combobox` / `ds-select` / `ds-search`:

- [~] **focus ring reads as a double outline on inputs** — **root cause found 2026-06-18 (was misdiagnosed).** The screenshot's double ring (outer pink + white gap + inner teal) was NOT the DS control's own border+shadow. User scoped the fix to pinkmoon only; DS lib left untouched. **DS-side follow-ups still open (real, separate from the leak):** (1) `ds-search` names its inner input with the over-generic `.input` class — a leaky surface any consumer `.input` reset bleeds into (combobox already scopes via `.combo-input`); consider renaming to a scoped class so the lib is immune. (2) ✅ **Token inconsistency FIXED 2026-06-18.** `ds-combobox` focus was on `--focus-ring` (2px `--surface-canvas` gap + solid primary = a genuine double-band, ugly on dark bg) while `ds-select`/`ds-search`/`ds-input`/`ds-dropdown`/`ds-number-stepper` use the softer `--focus-field`. Changed `combobox.component.scss` `:focus-within` `box-shadow: var(--focus-ring)` → `var(--focus-field)` (one line; lib build green, stylelint clean). The FIELD family is now 100% uniform on `--focus-field`; `--focus-ring` stays for actions/nav/inline (button/checkbox/radio/switch/tabs/link/menu/card/pagination/sidenav/date-picker/toast) — the deliberate two-tier system (fields → field-halo, actions → crisp ring), NOT an inconsistency. A theme-wide `focus type` switch (field/ring/B/C) is logged under Missing tokens / foundations. Live A/B/C comparison (incl. dark-bg strip + baseline-impl breakdown) → `presentations/pin-475-fields.html`.
- [ ] **"Glued field" / adornment composer — one bordered control from a leading select + trailing input (proposed 2026-06-18, Stas).** PIN-475's search bar needs a single field that reads as `[ "search by" select ▾ | divider | text input OR product autocomplete ]` — one shared border + one focus ring, fixed-width left segment, flexible right segment. `ds-select` can't be a leading addon: it has no fit-content width (it fills the host — already logged above) and no API to drop its own border/radius so it blends into a shared chrome. So the prototype had to build a LOCAL `app-search-scope` (custom dropdown segment + `ds-search`, stripping ds-search's border via `::ng-deep`). Proposal: a DS primitive for the general pattern — gluing `select + input`, `select + search`, `select + autocomplete/combobox`, `button + select` (split-button), `input + button` (e.g. search submit), etc. into one cohesive control. Sketch: a `ds-field-group`/`ds-input-group` container that (a) draws the single border + focus-within ring, (b) renders an internal divider between slots, (c) tells slotted DS controls to render "naked" (no own border/radius/shadow) via a context token or a `[grouped]` input, (d) lets each slot declare fixed vs flexible width. Precedents: Chakra `InputGroup`/`InputLeftAddon`, MUI `OutlinedInput` adornments, Ant `Input.Group`/`Space.Compact`, Bootstrap input-group. Without it every consumer re-hand-rolls the glue + `::ng-deep`-strips DS chrome (fragile, leaks). Pairs with the combobox fit-content + single-select-display items above (those are the leading-segment's blockers). Live local impl to mine for the spec: `prototype/projects/admin/src/app/shared/search-scope/search-scope.component.ts`.
