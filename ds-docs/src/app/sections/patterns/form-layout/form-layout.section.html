Two-column section pattern: title and description on the left, fields on the right. Fields stack vertically; naturally-paired controls (Start / End, City / Country) sit side-by-side. A footer anchors every form with a secondary Discard and a primary Save. The date fields are plain inputs because this demo shows layout; real forms use ds-date-picker (with mode="range" for a start/end pair) and ds-time-picker .

Validation & messages

Layout is only half a form — this is when feedback appears and where it goes. These rules keep the happy path unblocked and errors legible.

  • Gate submit on presence + not-in-flight only, never on format validity — a half-typed email must not disable the button, or the user faces a dead control with no explanation.
  • Judge validity inside the submit handler; that attempt is what reveals the messages. An early return from the handler that renders nothing is the silent-no-op bug.
  • Field errors live in the field's own message row. On a form that validates, turn on reserveMessage (off by default; per field, per form with dsReserveMessages , or app-wide via DS_CONFIG.field.reserveMessage ) so the first error does not shift the controls below it, and stack those fields with <ds-stack gap="none"> , since a reserved row already carries ~23px of trailing rhythm. Whole-request failures go in a ds-alert after the submit button — an error region above the inputs pushes every control down.
  • A rule checklist must change its icon, not only its colour — colour alone fails colour-blind users and forced-colors mode.

The fix is per-child rather than per-stack: give the children that carry no message row the same trailing space the reserved ones have, and leave the stack at gap="none". Reaching for gap="md" to rescue the odd child re-adds the doubled rhythm to every field.

Usage

  • Section description fits on one line — if you need two, the section is doing too much.
  • Pair natural counterparts (Start/End, City/Country) horizontally; everything else stacks.
  • Footer stays visible without scroll on common viewports; sticky-footer is acceptable on tall forms.
  • Inline edit is for single-field changes. Promote to a full form once two or more fields move together.
