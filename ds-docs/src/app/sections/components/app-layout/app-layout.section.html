Opening the rail from your own chrome

Below the lg breakpoint the rail becomes an overlay, and the button that opens it lives in YOUR topbar — so the layout cannot wire it up for you. Two routes, and picking the wrong one is the easy mistake. On a native button put dsRailTrigger on it: the directive toggles the rail and keeps aria-expanded and aria-controls correct. On a ds-icon-button do NOT — the directive's attributes would land on the wrapper, and the inner button is what a screen reader reads. Bind that component's forwarding inputs instead, off a template ref: [ariaExpanded]="layout.railOverlay() ? layout.railOpen() : null" and [ariaControls]="layout.railId" . These docs use the second route — the burger at the top of this page on a narrow screen is it.

Both attributes are dropped while the rail is NOT an overlay: above the breakpoint the rail is permanently in the layout, so aria-expanded="false" would state the opposite of what the reader sees.

Returning the reader to where they were

[restoreScroll]="true" remembers the scroll position per route and restores it — but only on a BACK, which is the whole design: returning to a list should return to the reader's row, while following a link into a new screen should start at the top. A history traversal arms it (back, forward, the mouse side button, Alt+← and an edge swipe all arrive as popstate), as does a reload, and a host that pushes instead of traversing can arm it explicitly with state: {{ '{' }} dsRestoreScroll: true {{ '}' }} . Any wheel, touch or key input cancels the pending restore, so it never fights a reader who has already started scrolling. These docs run with it on.

Resetting is separate from restoring, and it now has a switch: scrollReset is 'path' by default — the top only when navigation lands on a different PATH, so a search, a sort or a page step on the same screen keeps the reader's place. 'always' resets on those too, which is what a server-paged list usually wants, and 'never' hands the decision back to the screen — which can still call scrollToTop() itself. The input exists because owning the scroll CONTAINER had quietly meant owning the POLICY: a screen could ADD a reset and had no way to suppress one.

LayoutNavigationService is public for the same reason. Its pathChanged stream is the layout's own answer to "did we go somewhere else?" — `NavigationEnd`, path only, de-duplicated, and skipping any navigation that carries state: {{ '{' }} dsSamePage: true {{ '}' }} . Inject it instead of deriving your own: one consumer ended up with three answers that disagreed, because a `split('?')` keeps the fragment this one strips.

The offset is applied once the content is tall enough to hold it, watched with a ResizeObserver rather than a fixed frame count, and clamped at restoreScrollTimeout so a list that loaded 8 of 40 rows still lands near the right place instead of nowhere. A page that renders its own scroll position — a virtualizer decides which rows to build BEFORE it can be scrolled — should take the offset instead of letting the service assign it: inject(LayoutScrollService).consumePendingOffset() .
