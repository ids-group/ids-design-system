Opening the rail from your own chrome

Below lg the rail becomes an overlay opened by a button in your topbar. On a native button, add dsRailTrigger: it toggles the rail and syncs aria-expanded / aria-controls. On a ds-icon-button, do not - the attributes would land on the wrapper. Bind its forwarding inputs off a <ds-app-layout #layout> template ref instead: 

<ds-icon-button
  icon="menu"
  ariaLabel="Open navigation"
  [ariaExpanded]="layout.railOverlay() ? layout.railOpen() : null"
  [ariaControls]="layout.railOverlay() ? layout.railId : null"
  (pressed)="layout.railOpen.set(!layout.railOpen())" />

This site's burger uses the second route. Both attributes are dropped while the rail is not an overlay, since aria-expanded="false" would misstate a permanently visible rail.

[(railOpen)] is the open state. railLabel names the overlay dialog (unset falls back to DS_INTL.appLayout.railLabel). The open overlay traps focus; Escape or a scrim click closes it and returns focus to the trigger. The layout requires the application router (provideRouter).

Returning the reader to where they were

[restoreScroll]="true" remembers the scroll per route and restores it only on a history traversal (popstate: back, forward, mouse side button, Alt+←, edge swipe), on a reload, or on a navigation with state: {{ '{' }} dsRestoreScroll: true {{ '}' }} ; a link into a new screen starts at the top. Any wheel, touch or key input cancels a pending restore. These docs run with it on.

scrollReset decides when the content returns to the top: 'path' (default) only when the path changes, so search, sort or paging keeps the place; 'always' also on query/fragment-only navigation (server-paged lists); 'never' leaves it to the screen, which can call AppLayoutScrollService.scrollToTop().

AppLayoutNavigationService.pathChanged is the layout's own answer to "did we go somewhere else?": NavigationEnd, path only (it strips both query and fragment), de-duplicated, and skipping any navigation that carries state: {{ '{' }} dsSamePage: true {{ '}' }} . Inject it instead of deriving your own.

The offset is applied once the content is tall enough to hold it, watched with a ResizeObserver rather than a fixed frame count, and clamped at restoreScrollTimeout so a list that loaded 8 of 40 rows still lands near the right place instead of nowhere. A page that renders its own scroll position — a virtualizer decides which rows to build BEFORE it can be scrolled — should take the offset instead of letting the service assign it: inject(AppLayoutScrollService).consumePendingOffset() .

The rail footer on its own

<ds-sidenav-footer> is the one part of the rail a consumer configures rather than composes: it owns the profile row, the alert bell and the collapse handle. Both states below are the same element — [collapsed] switches it. The width comes from the sidenav, so a footer shown outside one needs a frame of its own.

The footer only emits collapse (collapseToggled) and sign-out (signOutSelected); the parent acts on them, so the collapse row here, left unbound, does nothing. A null searchProvider or alertItems keeps that row inert, and an empty profileRoute makes "Your profile" a no-op.
