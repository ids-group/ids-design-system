Clearable

[clearable] shows an inline × button when the field has a non-empty value. Defaults to true for type="search" and false otherwise — pass an explicit boolean to override.

Password toggle

On type="password", [passwordToggle]="true" adds an eye button that flips the field between masked and plain text. Two-way [(passwordVisible)] exposes the state.

Character counter

[maxLength] caps input length natively and shows a live current/max counter below the field — right-aligned, aligned with the hint.

Required vs optional

[required]="true" appends a red asterisk to the label; [optional]="true" appends the muted "(optional)" suffix. They are mutually exclusive — pick one.

Messages: error, warning, hint

A field takes all three and shows exactly ONE, highest first: error → validation errors → warning → hint . Only one line ever renders, so the field's height never depends on how many of them you bound. All three fields below carry the same hint ; the second adds a warning and the third adds both.

The control paints the state too, not only the line under it. An error takes a red border AND a tinted fill because it blocks submission; a warning and a success take the border alone, so an error still reads as the loudest thing in a form holding all three. One rule drives all nine bordered fields, off a data-field-state attribute on the host — style against that attribute rather than a class if you need to extend it.

The glyph on the message line

error , warning and success each bring a glyph; hint does not, because it is the resting text rather than a state and a form where every field carries an info circle reads as noise. Colour alone was the whole signal before — and in the light theme warning (#8A7400) against success (#156822) is a hue apart and nothing else, which is the case WCAG 1.4.1 is about.

Bind error and it shows at once — binding it says you have already decided. Everything else can come from the form control instead, and then you bind nothing: the field reads the control and waits for the first blur, so a required error never greets an untouched form. Both fields below are plain [formControl] with Validators and no message binding at all — focus one, leave it empty, and blur.

A form can raise a WARNING, not only an error. "Display name" above runs a validator that returns {{ '{' }} warning: 'Long runs of capitals are hard to scan' {{ '}' }} — the reserved kind exported as DS_FIELD_WARNING_KIND . The field paints the warning state and shows the text, but stays VALID: aria-invalid is not set and a submit guard reading validity is not blocked. Angular's AbstractControl has no channel for an advisory remark — only errors and the validity derived from it — so this rides in errors under a kind the DS treats as non-blocking. It works from both form systems: a reactive validator's KEY becomes the kind, and signal forms' own ValidationError already carries one.

The text for required and minlength above comes from one shared map — provideDsConfig({{ '{' }} field: {{ '{' }} errorMessages: … {{ '}' }} {{ '}' }}) on this section — because Angular's built-in validators carry a detail object and no wording. A validator that supplies its own message wins over the map: "admin" is rejected by a custom validator returning {{ '{' }} taken: 'That handle is already taken' {{ '}' }} . In signal forms the same thing is written at the validator — required(path, {{ '{' }} message: … {{ '}' }}) — and the field needs no binding there either, because errors and touched are the names Angular's FormUiControl contract binds automatically.

Reserved message row

reserveMessage (default off) holds a message line's height even when there's no hint or error, so a form doesn't reflow the moment validation appears. Turn it on with [reserveMessage]="true" on a single control, or with the dsReserveMessages directive for a whole form (below). The reserved row sits ~23px under the control, so stack reserved fields tighter — <ds-stack gap="none"> — than bare ones, or the gap reads as a hole.

For a whole form, put the dsReserveMessages directive on it instead of binding every control: <form dsReserveMessages>…</form> . It provides DS_CONFIG for its subtree, merged with the config above it, and a field's own [reserveMessage] still wins. It applies to fields declared inside the host — projected content keeps the injector of the template it was written in.

Whole form at once

Put dsReserveMessages on the form and every field declared inside it reserves — no per-control binding. A field's own [reserveMessage] still wins.
