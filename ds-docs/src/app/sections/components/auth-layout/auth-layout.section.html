The scaffold for the screens in front of the login — counterpart to ds-app-layout , which only ever covers what sits behind it.

Sign-in, forgot password, reset and MFA are the same four parts every time: a brand lockup, an optional tagline, one card holding the form, and a support line underneath. The brand row is the sidenav's row — same brand / logoLetter / [dsBrandName] contract, and an accent letter-mark tile of its own — close enough that the mark a user meets on the login screen reads as the mark that greets them in the rail, but not identical: the rail's is a fixed 28px at weight 800, this one 24-32px at 700, and the two carry separate token hooks, so retinting the mark means setting both.

Set the brand once, not per screen. provideDsConfig({ brand: { name, logoLetter, tagline } }) answers all three for this layout AND for ds-sidenav , which asks the same questions — an app that has six auth screens was binding the same values six times. Each field resolves on its own: an element input beats the config, so one screen can differ without restating the rest, and brand="" drops the wordmark while a logoLetter in the config still paints its tile. Clear both to give a screen no brand row at all.

The two-tone wordmark stays projected — there is deliberately no accent in the config. A config can only carry a string, so an accent would have to be found by splitting that string back apart, which is exactly the guessing [dsBrandName] exists to avoid. Provide the plain name in the config and project the accented version on the screens that want one; the projection wins over both.

Everything inside the card is yours: the default slot projects straight into it, and the layout deliberately leaves your headings and form alone so its type scale never fights your screen's. The support line goes into [dsAuthSupport] and renders as the page's contentinfo landmark when this layout IS the page — nested inside another layout's main (as on this docs site) it is a plain footer. Leave it out and the footer collapses. The card itself is an article, which is not a landmark: on a standalone auth page set landmark="main" so a screen-reader user can jump to the form.

On a short screen the chrome compresses, not the card

A landscape phone leaves about 330px of viewport, and the furniture this layout puts around your card — block padding, the column gap, the letter-mark tile, the wordmark, the masthead's inner gap — used to cost ~219px of that before your form got a single pixel. All of it now clamps against svh , so at ~330px the same chrome costs ~131px. Every multiplier reaches its maximum at a viewport 800px tall or more — which is a viewport height, not a screen size: a 1366x768 laptop lands near 630px after browser and OS chrome, and a 1080p screen at 150% display scaling near 585px, so plenty of desktops render the compressed furniture too. Type is deliberately not part of it: the wordmark and the tile's glyph stay fixed, because in a row whose height the tile already sets they cost nothing to shrink and only flatten the brand against the tagline.

The demos above cannot show it: the clamps read the real VIEWPORT, and a framed demo only shrinks its own box. Make the browser window short — or rotate a phone — and watch the padding, the gap and the wordmark come down together.

svh and not dvh : the dynamic unit changes as a mobile URL bar hides, which would resize the wordmark and re-space the column while the reader scrolls. Setting any of --ds-auth-layout-pad-block , -gap or -mark-size to a fixed value opts out of the compression for that one dimension.

What this does not promise. A card taller than the space left still scrolls, and should — the fix is for the LAYOUT never to be the reason. Compressing rather than pinning is deliberate: the same exercise elsewhere takes the masthead and footer out of the flow with position: absolute , which frees more room but lets that chrome overlap a tall form instead of scrolling past it. A card here holds whatever you project into it, so overlap is the worse failure.

Why it centres with auto margins

The full-height box is the layout's own host, and there is only one of it — the hand-rolled version this replaces nested a 100vh wrapper inside a 100dvh one, which scrolls a page whose content fits. Inside it the column is centred with auto margins rather than centre alignment. On a normal page the two are the same, because the host is free to grow and a tall form simply lengthens it. They differ once the host cannot grow — when you embed the layout by setting its min-height token to 100% in a fixed-height parent. There, centre alignment puts a form taller than the box above the scroll origin, out of reach of any scrolling; auto margins collapse to zero instead, so the form pins to the top padding edge and scrolls from there. Both demos above are the real component with that token lowered to fit this page.

The notch needs one line from YOUR app

This layout pads itself by env(safe-area-inset-*) , so a notched phone in landscape does not put the card under the cutout — and ds-bottom-sheet does the same for the home indicator. Those insets are 0 until the host document opts in , and a library cannot do it for you: it lives in the viewport meta tag, which belongs to your index.html . 

<!-- your index.html -->
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover" />

Without it a cutout is not enough — the browser simply reports 0 for every inset and the padding you see is the plain one. This site sets it, so the behaviour above is the real thing rather than a description of it.
