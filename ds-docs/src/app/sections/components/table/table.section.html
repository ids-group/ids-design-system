Re-fetch indicator — existing rows stay visible behind a translucent overlay with a centred spinner. Use [loading]="'overlay'" for refresh / re-sort / filter-change.

Loading · let the table choose

[loading]="true" resolves the two above by the row count: skeleton while there is nothing on screen, overlay once there is. Prefer it. Which treatment is right is not a preference — replacing visible rows with placeholders throws away what the reader is looking at, and dimming an empty card announces nothing about what is coming — and the table is the only place that holds both halves of the condition. Every list screen was otherwise writing the same items().length > 0 ? 'overlay' : 'skeleton' line; one consumer feature had three copies of it.

The empty state is a claim about the data — “there are none” — so the table withholds it until it has finished asking. Both loading modes suppress it: the same table with [loading]="'overlay'" and zero rows shows its spinner and no message, where it used to paint “No records match your filters” underneath one. Pagination · sticky column

[pageSize] turns on client-side pagination (select-all then scopes to the current page); [stickyFirstColumn] pins the first column on horizontal scroll; sortMode says who sorts — "server" (the default) emits (sortChange) and leaves ordering to you, "client" has the table reorder its own rows and is what a table holding EVERY row wants, and "none" drops the affordance so a sortable column cannot draw a header that does nothing. 12 rows across three pages; [animateHeight] tweens the body height between pages (page 3 has only two rows) instead of snapping. For server-side paging, bind [total] to the full row count and hand the table one page at a time — it then drives the pager off total and skips its own slicing. Add [scrollToTopOnPageChange] to scroll the table back into view on a page change — handy when the pager sits below a long table.

Clickable rows · drawer detail

[rowInteractive]="true" turns every row into a keyboard-operable control — pointer cursor, hover and pressed tints (passive tables render none), focus ring, Enter/Space — and (rowClicked) emits the row. The classic master-detail wiring: clicking a row opens a ds-drawer with the record, and [activeRowId] keeps that row highlighted (plus aria-current ) while the drawer is open. Controls inside cells (checkboxes, menus) stop propagation, so they never trigger the row click — and neither does finishing a text selection, so cell values stay copyable by mouse.

Row actions · kebab menu

[rowActions] renders a trailing ⋮ column — the button opens a menu of the configured items and (rowActionSelected) reports the chosen action together with its row. A per-row disabled predicate greys items out (here Delete is blocked for completed records), and disabledReason puts the WHY on the item's second line — a greyed item that does not say why is the same dead control as a greyed button.
Where an action does not APPLY to a row, use hidden rather than disabled : greying leaves every row with a permanently dead half, which is what happens when one status offers Edit + Launch and another Revert + Delete. Relaunch below is hidden except on completed records. If every item of a row is hidden the kebab is not rendered at all, so a row with nothing applicable does not open an empty menu. The kebab stops propagation, so on a [rowInteractive] table a menu click never fires (rowClicked) . A hand-built action column with no visible header should give its TableColumn an srLabel so screen-reader users still hear a column name.

Column picker · reorder

Resizable columns

[resizableColumns]="true" adds a drag handle to each header's right edge. Widths are two-way bindable via [(columnWidths)] (a Map<key, px> ), seeded from any column.width .

The first resize records a width for EVERY visible column, not just the one you dragged — deliberately. Until then the untouched columns are auto-sized, so the browser redistributes whatever the dragged column gives up and columns nobody touched visibly jump. Measuring them all once, at the first grab, keeps the auto-sized geometry instead of losing it. The consequence to expect: if you persist [(columnWidths)] , one drag fills the map for the whole row. That is the saved layout, not a leak — and a second drag adds nothing further.

Inline editing

Columns marked editable: true (Record, Venue, Capacity here) turn into an input on double-click; Enter or blur commits, Escape cancels. The table stays data-agnostic — it emits (cellEdited)="…" with {{ '{' }} row, key, value {{ '}' }} and the consumer applies the update.

Persisted layout & export

[persistLayout]="true" with a storageKey round-trips the column order, widths and hidden set through localStorage , so reorder a column or hide one, reload the page, and it stays. Without a key nothing is stored — two tables would otherwise overwrite each other. [exportButton]="true" renders the CSV button; a server-paged table passes [exportFetcher] so the export covers the whole set instead of the page it holds.

Toolbar slot · the export button anywhere

A row above the table, filled through one [toolbar] slot, for controls that act on THIS table: a search box, a status filter, a refresh. Project a handful of controls and the row lays them out — flex, wrap, 8px gap — so the ordinary case needs no CSS of yours. Project one element of your own instead and the layout is entirely yours; the row's flex then has a single child and stays out of the way. It disappears when nothing filled it and exportButton is off, so a table that uses neither is unchanged. Filters that belong to the PAGE still belong in a ds-filter-bar above it — the slot is for the ones that would otherwise read as page furniture one card away from the rows they narrow.

One slot rather than a start/end pair, and that was a correction. The fork this replaces had exactly one, its right-hand side being the component's own buttons — and all four screens that used it projected a container of their own anyway, each writing the same four declarations. A second slot would have been API nobody had asked for, and the layout it promised to own is one the consumer writes regardless when their case differs.

The export button does not have to live there either. runExport() is public and so are exporting() and exportStatus() , so a button in a page header or a filter bar runs the same path — the exportFetcher call, the download, the in-flight state and the live-region announcement. Leave exportButton off and drive it yourself.

Sizing a column to its content

width: 'content' on a column sizes it to its widest cell and stops it wrapping, leaving the slack to the columns that should absorb it. An auto-layout table spreads leftover width evenly, so a status or a figure ends up as wide as its own header while the name column that should take the space does not. A pixel width cannot express that — pin one column and the rest still spread. Below, Status and Budget are 'content' ; Project and Owner share what is left. Dragging a column's edge still wins, since that is a deliberate pixel width.

Server sort · a host that answers with its own default

The shape a server-paged list actually has: [sortKey] and [sortDir] are bound ONE-WAY from the host's own state (usually a computed over the URL), and (sortChange) is where it hears about a click. This host's default is Owner descending , and it answers a cleared sort by returning to it — the case that used to leave the header marking nothing over sorted rows.

Third click on the same column clears it, so watch the header: after the clear the highlight must land back on Owner ▼ . Host state: {{ serverSortKey() }} · {{ serverSortDir() ?? 'null' }}

The same thing two-way, when the host has no opinion to defend

sortKey and sortDir each have a matching Change output, so [(sortKey)] and [(sortDir)] work: the table writes the host's state and the host reads it back, with no handler to write. Below is the demo above with the handler deleted and nothing else changed.

What you give up is the third click. Clearing a sort sets sortDir to null and the rows come back unsorted, because there is nowhere left to say "then fall back to Owner descending". Prefer two-way where any sort state is equally valid — a saved view, a URL you round-trip — and the one-way pair plus (sortChange) where the host owns a default it has to be able to restore. Truncation · full-text popover

truncate: true ellipsis-clips a text column at its width (240px when unset). The full value sits in the hover tooltip, and clicking a clipped cell opens it in a popover — an unclipped cell passes the click through to the row.

Only columns that asked for it are watched, and that is the point. Clip detection runs on cells in a truncate column, not on every overflowing cell in the table: a click handler on every <td> would swallow the row click on an interactive table. Within such a column it does look deeper than the cell itself — a dsCellTemplate puts the ellipsis on a descendant, so testing only the wrapper would miss it.

Sticky horizontal scrollbar

[stickyScrollbar]="true" hides the scroll container's native bar and pins a proxy scrollbar to the bottom of the viewport while the table is on screen — on a tall, wide table the horizontal bar stays reachable without scrolling to the table's end. Wide fixed column widths force the overflow here.

Server-side filtering, and a filter of your own

Header filters default to filterMode="server" : the table tracks columnFilters without filtering anything, so your request drives the rows; pass the real domain through columnFilterOptions . That is the right default because a paged table filtering locally would filter what the server already filtered, over a checklist offering only the values on THIS page. Declare filterMode="client" when the table holds every row and should filter them itself — there is a dev warning for the giveaway case, a filterable column on a table that binds no `total` and declares no mode. filterMode="none" drops the affordance entirely.

When the criterion is not a list of values — a date range, a numeric threshold, an async lookup — project the panel instead. The table keeps the header button, the popover and the active-filter styling; only the contents change. It cannot know whether YOUR criterion is set, so active is how the highlight is told.

  <ds-button size="sm" (pressed)="apply(); close()">Apply</ds-button>
</ng-template>

What a screen reader is told

Sorting and paging are read off the header and the pager by everyone else; the table now says them out loud too. One role="status" region carries "Sorted by Owner, ascending" and "Showing 1–25 of 240", with loading taking precedence while it lasts — announcing a new sort order over rows that are still being replaced describes a state the reader cannot inspect. Both strings are inputs ( sortAnnouncement , rangeAnnouncement ) taking the facts and returning the sentence, so translation and word order stay yours; return an empty string to stay silent. The first render is silent regardless — aria-live="polite" announces changes, not initial content.

Virtual scroll

10 000 rows. With [virtualScroll]="true" only the rows in view are in the DOM, padded above and below by two spacer rows that stand in for the rest — so the scrollbar is the full length of the data and the row count in the DOM stays flat. It needs maxHeight , because a bounded scroller is the viewport it windows against.

Every row must be exactly virtualRowSize tall — that number is the only thing telling the maths where a row starts, so one row that grows puts every offset below it out by the difference. Virtual mode therefore fixes the row height from that same input, forces table-layout: fixed (auto layout re-measures against whichever rows happen to be rendered, and the columns twitch as you scroll) and keeps cells to one line. Row EXPANSION is suppressed for the same reason, with a dev warning; sorting, selection, sticky header and sticky first column all keep working.

Lazy loading

The same 10 000 records, except the table starts with none of them. With [lazy]="true" the window asks for the range it is about to show through (lazyLoad) , and every index the host has not filled yet renders a skeleton row. Scroll fast and you outrun the fetch — that is what the skeletons are for.

data is a SPARSE array total long: write each fetched row at its absolute index. The scroller is sized from total , not from what has arrived, so the scrollbar tells the truth from the first frame. The demo answers after 600 ms; a request already in flight is never re-sent.
