Priority+ filter row: as many filters as fit, the rest behind "+N more".

Every admin list past three filters hits the same wall — the row wraps to a second line on a laptop, or someone hand-rolls an overflow menu. Each filter goes in an ng-template carrying the width it should occupy, and the bar decides the split from those numbers plus one ResizeObserver on the row. It never measures the filters themselves: they would have to be in the DOM to be measured, so anything that did not fit would flash into view before being taken away.

Drag the handle to resize the frame — the filters collapse into the panel from the right as room runs out, while anything marked dsFilterBarTrailing keeps its place throughout. Mark each trailing control rather than wrapping them in a div: the bar owns that group's gap and alignment, and a projected wrapper is a plain block whose children would stack. The group sits outside the measured row, so flexbox subtracts its width first and the arithmetic needs no allowance for it.

If one component genuinely has to hold two trailing controls — the usual reason was a Clear that must cancel a debounce armed on the search beside it, and that reason is gone: ds-search cancels its own pending keystroke when the host writes value, so a bar-level Clear no longer needs to live in the same component — then mark that component and give its :host the three declarations the bar would have applied. They are the bar's own trailing rule, and the gap reads from the same token so the two cannot drift.

Sizing the "+N" trigger

triggerSize matches the trigger to the filters beside it — default md. The bar cannot work this out on its own: dsFilterItem carries a WIDTH, and the filters are arbitrary projected controls whose own size it never sees. Left unset beside sm filters, the trigger stands 8px taller than everything next to it, since the row aligns on flex-end.

What the width buys

The declared width is a contract rather than a hint: the bar sizes each slot to exactly that number, so the arithmetic that decided the filter fits is true by construction, and a filter is the same width in the panel as it was in the row — no resizing as it crosses over. A control that would rather be wider is narrowed instead of being allowed to break the row.

Crossing that boundary does destroy and re-create the view, so a control's internal state — an open dropdown, focus — does not survive a resize that collapses it. Its value does: that lives in your own signal or form control, which is why the demo above keeps every selection while you drag. The trigger carries the count as text and aria-expanded, and the panel is a focus-trapped dialog; there is exactly one copy of each filter in the accessibility tree, because the filters move rather than being rendered twice and hidden.
