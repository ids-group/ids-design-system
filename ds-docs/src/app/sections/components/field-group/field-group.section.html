Several controls, one bordered box — scope + search, amount + unit, input + action.

The group owns the border, the radius, the divider and a single focus ring; the controls inside render naked. A segment knows it is inside a group because the group provides DS_FIELD_GROUP , which it injects — nothing to remember per child, and no way to forget it on one of them and leave a stray border mid-row.

Segments hug their content. Mark the one that should take the slack with grow .

Trailing action, and a unit after the value

Any supported control can be a segment, in any order — a ds-button at the end is the same mechanism as a ds-select at the start.

Go

Every supported control

Six controls can be segments: ds-input , ds-select , ds-search , ds-autocomplete , ds-date-picker and ds-button . Not ds-number-stepper (already a composite of its own) or ds-multi-select (its chips wrap, which a fixed-height row cannot take).

Sizes, error and full width

size is the field family's scale, so a group lines up with a plain field beside it. invalid colours the whole box: a single segment cannot be in error on its own, because the border is not its own.

Saying what is wrong

The group takes the same pair every field takes. error is a string: it turns the state on and carries the text, in one message under the whole row rather than one per segment. invalid is the flag for when the text lives elsewhere — a form-level summary — and hint uses the same row.

Every segment carries aria-invalid while the group is in error, and every segment points at the one message through aria-describedby — a reader who tabs straight to the second segment hears the error there too, which is the whole reason the state is not announced on the group element itself.

Do not give a grouped control a label or a hint : its message row would break the glued line, so both are suppressed. A group-level label is not built yet — put one above the group with your own markup until it is.
