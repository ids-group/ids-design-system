Colour is layered in three concerns — a theme-independent base palette, the theme role maps (light / dark), and optional brand overlays. Light is the default; dark is opt-in. Components only ever read semantic roles, so swapping a theme or brand re-skins everything without touching component code.

Activation

The active theme is a single attribute on the document root (<html>) — a whole-document switch, not per-subtree.

  • nothing — light (default)
  • <html data-theme="dark"> — dark
  • <html data-theme="light"> — explicit light (same as the default)

There is no automatic prefers-color-scheme switch — light is deterministic by default. To follow the OS, opt in from your app bootstrap; set the attribute before first paint to avoid a flash:

Three layers

Base palette (themes/_base-palette) — theme-independent primitives at :root: hue ramps + HSL channels, --static-ink (never flips), fonts.
Theme / roles (themes/_semantic + themes/<t>/) — the semantic role map (--primary, --surface-*, --text-*, --neutral-*, --focus-ring). Light at :root, dark at :root[data-theme='dark'].
Component / scale (styles/_tokens, *.component.scss) — --space-*, --radius-*, --ds-*, motion. Theme-independent.

Hard rule: components never read base-palette primitives (--blue-600) directly — only Tier-2 roles (--primary, --text-secondary) or component tokens.

Sibling themes, not a patch

Light and dark are sibling role maps sharing the base palette and the same role structure. The dark block declares the complete token set, so :root[data-theme='dark'] fully replaces light rather than delta-patching it. On-fill text is the literal white, or the theme-stable --static-ink where the fill is light, so neither flips with the neutrals.

Writing your own theme or brand

Two levers. A brand is a thin overlay scoped by attribute ([data-brand="X"]) — override the brand hue ramp (--blue-*) and/or --primary plus a few roles. A full theme is a new sibling role map.

You author on light — the default. Dark is a self-contained sibling, so a light-authored brand does not automatically carry into dark. If the brand must also restyle dark, add a separate [data-theme='dark'][data-brand="X"] block.

Leave --primary-hover / --primary-pressed to the DS color-mix() derivation (toward black in light, toward white in dark). Full guide: themes/README.md.

App-level defaults — provideDsConfig

Tokens answer “what does it look like”. This answers the other repetition: an input whose value an app writes identically on every element. One consumer binds [stickyScrollbar]="true" on all 35 of its tables and size="sm" on 146 buttons — not a per-element decision, a house default restated 146 times, and every new element is one forgotten binding away from looking wrong.

Precedence is input → config → built-in, so a screen that differs still binds the attribute and wins. Nothing changes for an app that provides nothing: every built-in default is what it always was. Provide it at the app root, on a Route, or on a component — the config resolves through the injector chain and a nested call MERGES with the one above it, section by section. 

{{ configSnippet }}

control.size is not the same axis as [data-density]. The density tier rewrites hit targets and padding in CSS for a route; this picks which of the three declared sizes a control renders at. An app can use both.

Worked example — a square brand

The most common whole-brand change, and the one most often done the long way: a consumer audit found twelve scattered --ds-<component>-radius: 0 declarations written one component at a time. Four lines replace all of them. 

{{ squareSnippet }}

Three role declarations do it, and as of 2026-08-10 that is finally true. Measured: on a component page, zeroing --ds-radius-inner, -control and -panel squares most rounded surfaces, and it is worth knowing which ones it does not. Thirty-one declarations across nineteen components still read the scale directly rather than a role — the menu panel, the toast, split-button and button-group segment corners, the sidenav footer, the colour-picker swatches and a dozen others. Zeroing the three roles leaves those at their scale value. --radius-pill is out of scope by design: switch tracks, avatars and status dots are round by shape, not by style.

Zeroing the SCALE instead is the blunter option, and it reaches everything the roles miss: those thirty-one declarations, plus the focus-ring radii, which deliberately follow the scale rather than a role — a ring traces a box, it is not a surface a brand designs. Use it if you want the corners squared everywhere.

Leave --radius-pill alone either way. A switch track, an avatar and a status dot are round because of what they are, not because of the brand — verified: with the scale zeroed, the switch track stays fully rounded because it resolves the pill token instead.
