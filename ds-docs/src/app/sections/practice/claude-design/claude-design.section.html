A Claude Design project can hold this library itself, so its agent builds screens out of the real components rather than something in their style. This page is how that works, what you run, and which files are authored versus generated.

What the design tool actually loads

The agent's code renders React.createElement(window.IdsDs.<Component>) . The contract is narrow: expose React components on window.IdsDs , and React arrives separately as a global (the project's _vendor/react*.js). React is not inside _ds_bundle.js, and nothing inspects what else is, so an Angular runtime can ride along inside it.

A card holds no React. It is one HTML page per data-claude-design block of a ds-docs chapter, rendering that chapter's section tag on the bundle: 

<script>window.__dsSectionsOnly = true</script>
<script src="_ds_bundle.js"></script>
<div class="ds-page"><ds-docs-components-button></ds-docs-components-button></div>

build-cards.mjs writes the cards into .design-sync/upload/ , and measure-cards.mjs records their heights in viewports.json . snapshot-cards.mjs runs last: it freezes every card outside live-cards.txt into static HTML that links the shared _ds_cards.css . What to mark is in .design-sync/CARDS.md .

Why the components are generated, not ported

Every component is registered as a custom element and its React wrapper is generated from the AST by gen.mjs , so there is no second implementation to drift. The cost is the Angular runtime inside the bundle, fixed as the library grows.

npm run check:cards is the whole chain above in one command, and the only form that works in a tree which has not built yet.

Publishing is a separate, deliberately gated flow: read the project, lock a plan, then write. The tool rejects any path outside the locked plan, and the plan is shown to a human before anything is written.

Authored, generated, or remote

The repository commits the sync inputs and the built tree at .design-sync/upload/ . Only _ds_sync.json lives in the project alone, so its absence here is not drift.

Two rules that will bite otherwise

  • An agent composition sets its state as INITIAL props, never toggles it after mount. A slot behind a condition works, nested DS components included, as long as the gate is true when the element connects. Toggle it later and the projected wrapper survives while the custom elements inside it are destroyed. So an overlay passes staticPreview or open at creation, and a table that shows bulk actions passes its selection at creation.
  • A component used inside another component's template registers under an alias. A custom element nested in another's template loses both its projected content and its inputs, so the generator gives those an ds-x- tag no template mentions. The React wrapper emits the alias, so nothing changes for a caller and the tag never surfaces in a design.

Attribute directives have no tag to register, so they are absent from the generated surface; manual-surface.json lists them. Only dsTooltip would be missed, and a tooltip is hover-revealed — a static design card has no hover, so it would show nothing anyway.
