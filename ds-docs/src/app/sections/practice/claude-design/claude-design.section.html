A Claude Design project can hold this library itself, so its agent builds screens out of the real components rather than something in their style. This page is how that works, what you run, and which files are authored versus generated.

What the design tool actually loads

A preview card in the project is a plain HTML page loading four classic scripts, in this order, and rendering a React element from a global: 

_vendor/react.js  →  _vendor/react-dom.js  →  _ds_bundle.js  →  _preview/<Name>.js

So the contract is narrow: expose React components on window.IdsDs, and React arrives separately as a global. React is deliberately NOT inside the library bundle. Nothing inspects what else is in there, which is what makes the second route below possible.

Why the components are generated, not ported

The first attempt re-implemented every component in React over the compiled CSS — around 11 000 hand-written lines. It was correct when written and needed a parity gate, because nothing else can tell that a template has moved on. One month of upstream drift cost it 213 divergences: 53 components with changed sources, 122 missing props, 6 components with no counterpart at all. It was deleted on 2026-09-01.

What replaced it registers every component as a custom element and generates the React layer from the AST. There is no second implementation, so there is nothing to drift: the same month of upstream cost it one gen.mjs run, and the surface grew from 81 elements to 85 on its own. The price is about 135 KB gzip more over the wire for the Angular runtime — fixed, while the library keeps growing.

Publishing is a separate, deliberately gated flow: read the project, lock a plan, then write. The tool rejects any path outside the locked plan, and the plan is shown to a human before anything is written.

Authored, generated, or remote

The repository commits sync INPUTS only. Everything with an underscore prefix in the project is an output of the publish step — reading their absence here as drift is a mistake that has been made.

@for (file of files; track file.path) {
{{ file.path }} {{ file.role }}
{{ file.what }}
}

Two rules that will bite otherwise

  • A preview sets its state as INITIAL props — never toggles it after mount. A slot behind a condition works, nested DS components included, as long as the gate is true when the element connects. Toggle it later and the projected wrapper survives while the custom elements inside it are destroyed. So an overlay preview passes staticPreview or open at creation, and a table preview that shows bulk actions passes its selection at creation.
  • A component used inside another component's template registers under an alias. A custom element nested in another's template loses both its projected content and its inputs, so the generator gives those an ds-x- tag no template mentions — 31 of 85. The React wrapper emits the alias, so nothing changes for a caller and the tag never surfaces in a design.

Attribute directives have no tag to register, so the fifteen of them are absent from the generated surface. Only dsTooltip would be missed, and a tooltip is hover-revealed — a static design card has no hover, so it would show nothing anyway.
